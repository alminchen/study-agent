step1-chat 代码说明书

这是一份面向学习和复盘的完整说明书，按“前端入口 -> 网络层 -> 服务端编排 -> 工具 / RAG / 多 Agent -> 防护与统计”逐层解释当前项目的执行逻辑。

Vue 3 + Vite + TypeScript Express 后端 SSE 流式聊天 ReAct / RAG / Multi-Agent MCP / Tracing / Evals
说明：本文档只解释当前实现的代码逻辑，不修改代码，不引入新功能。

1. 项目目标

当前项目的核心目标，不是单纯做一个聊天框，而是做一个前端开发者能理解、能调试、能复用的 AI 应用样板。

  • 普通聊天：支持流式输出、多轮对话、模型切换、会话管理
  • 工具调用：天气、时间、知识库检索等工具可见、可调、可回填
  • RAG：文档检索、重排、引用、空结果兜底
  • Agent：ReAct、多步工具循环、Supervisor-Worker 编排
  • 工程化：Tracing、Evals、Token 统计、降级、防注入

2. 总体结构

项目可以分成四层：

  1. 前端页面层：负责输入、展示消息、展示工具轨迹与知识库命中
  2. 前端状态层：负责消息、模型、模式切换、持久化和中断控制
  3. 网络层：负责向后端发起 SSE 或 JSON 请求，并解析事件流
  4. 服务端层：负责聊天、工具执行、RAG、Multi-Agent、统计与安全防护
你可以把它理解成：UI 只负责表现，真正的决策与编排都在服务端。

4. 前端执行流程：从输入到消息落地

前端最重要的文件是 src/composables/useChat.ts。它负责把 UI 操作变成真实的聊天流程。

1

初始化状态

页面一加载，就会从 localStorage 恢复：

  • 当前是普通聊天还是 RAG 模式
  • 当前选择的模型
  • 历史消息
  • 是否打开“搜索知识库”

这样刷新页面后不会丢会话，也不会把不同模式的历史混到一起。

2

发送消息 send()

用户提交内容后，先做三件事：

  1. 去掉首尾空白
  2. 拼成一条 user message
  3. 把它加到消息列表并持久化

然后根据模式分流：

  • 普通聊天：走 runStream()
  • RAG 问答：走 runRag()
2.1

前端数据组装：history 是怎么来的

send() 不会直接把单条用户消息丢给后端，而是先把它拼到当前会话历史里，形成完整的 history：

  • 先取当前输入，trim 后生成一条 user 消息
  • 把这条消息追加到 messages
  • 把追加后的整段列表作为本轮请求上下文
  • 普通聊天和 RAG 各有一份历史，互不污染

这一步很重要，因为模型不是只看“这次输入”，而是看“这一轮加上之前所有上下文”。

3

普通聊天 runStream()

这个方法负责 SSE 流式输出。它会先创建一个空的 assistant 占位消息，然后边读边更新内容。

  • 创建 AbortController，支持中断
  • 把空 assistant 先插入消息列表，保证 UI 立即有反馈
  • 调用 streamChat() 发起请求，把 history、model、searchDocs 发给后端
  • 收到 delta 就拼接到最新 assistant 上
  • 收到 tool trace 就写入调试面板
  • 收到 usage 就更新 Token 面板
这里最容易出问题的是失败兜底。如果请求失败但 assistant 占位没被替换，就会留下空气泡。当前已经补了兜底文案。
4

资料问答 runRag()

资料问答不走 SSE，而是一次性拿 JSON 结果。

  1. 找到最后一条 user 作为 question
  2. 把它前面的历史作为 prior
  3. 调用 askRag()
  4. 拿到 answer / hits / usage 后再落地到 assistant 消息

这种方式适合 RAG，因为 RAG 的输出更像一个完整答案包，而不是持续增量输出。

4.1

RAG 数据组装：question 和 prior 怎么拆

runRag() 会把最后一条 user 单独拿出来当 question，再把它前面的消息切成 prior：

  • question 只放当前要问的问题
  • prior 只放当前问题之前的 user / assistant
  • 最后一条 user 不会重复进 history
  • 前端收到 JSON 后，再把 answer、hits、usage 组回 assistant 消息

这能避免同一个问题在 prompt 里出现两次，也能让检索问答和普通聊天分得很干净。

5

重试 retry() 与停止 stop()

retry() 会取掉最后一条 assistant，再重新走一次当前模式的请求。

stop() 则是直接 abort 当前请求。

这两个动作都依赖 AbortController，所以停止流式输出是可控的，不会只停 UI 不停网络。

5. 流程扭转：一个请求是怎么“转向”的

你特别提到“流程扭转”，这里专门把项目里最关键的分支和状态切换讲清楚。所谓扭转，就是同一轮用户输入，在不同条件下会走到不同链路。

5.1 从 UI 到后端的第一层扭转

  1. 用户输入内容后，先进入 useChat.send()
  2. 如果当前是普通聊天，进入 runStream()
  3. 如果当前是 RAG 模式，进入 runRag()
  4. 两条路都不会直接在前端生成答案，而是交给后端

5.2 普通聊天里的第二层扭转

  1. 前端根据当前模式把消息发到 /api/chat 或 /api/chat/multi
  2. 单 Agent 路径进入 createChatStream()，多 Agent 路径进入 compileMultiAgentGraph()
  3. 如果没有 API Key 或显式 Mock，直接转到假流式输出
  4. 如果有真实模型，继续转入 ReAct 编排

5.3 ReAct 里的第三层扭转

ReAct 是整个项目里最典型的“条件转向”逻辑。

  1. 先问一次模型
  2. 如果模型没有 tool_calls，说明答案已经完整，直接结束
  3. 如果模型有 tool_calls，先执行工具
  4. 工具结果回填到 messages 后，再回到 askModel
  5. 如果轮次超过上限，强制结束，防止无限循环

5.4 RAG 里的扭转

  1. 进入 runRag() 后，先把当前问题和历史拆开
  2. 后端先做检索
  3. 如果命中为空，直接返回固定文案，不再调用模型
  4. 如果有命中，才继续拼 prompt、调用模型并返回答案

5.5 多 Agent 里的扭转

  1. 用户问题先到 Supervisor
  2. Supervisor 判断任务应该交给哪些 Worker
  3. graph 把任务分发给对应 Worker
  4. Worker 可能继续自己的 mini ReAct
  5. Worker 完成后把结果汇总回主流程

5.6 流程扭转的核心原则

  • 先分模式，再分链路
  • 先判断有没有资料、有没有工具、有没有 API
  • 能提前结束就不要继续问模型
  • 每次转向都要有明确的状态依据，而不是靠“感觉”跳转
这部分是整套系统最值得理解的地方。你不是在看一个“聊天接口”，而是在看一套根据状态和条件不断转向的任务流。

6. 网络层：streamChat() 怎么工作

src/api/chat.ts 负责把前端消息发到后端，并把 SSE 逐条解析回来。

6.1 请求阶段

  • POST 到 /api/chat/multi（当前实现如此）
  • 请求体包含 messages、model、searchDocs
  • messages 是前端已经拼好的整段对话历史，不是单条输入
  • searchDocs 只是一个布尔开关，告诉后端这一轮是否要走资料搜索
  • 请求失败时直接把错误回调给前端

6.2 响应阶段

  • 如果返回不是 2xx，直接报错
  • 如果没有 body，说明浏览器不支持流式响应
  • 拿到 body 后通过 getReader() 逐块读取

6.3 SSE 解析阶段

服务端返回的是一段段 data: ...\n\n 格式的数据，前端会按事件切分。

  • delta：拼接到 assistant 正文
  • type = usage：更新 Token 统计
  • type = tool_call：记录模型准备调用了哪个工具
  • type = tool_result：记录工具返回了什么
  • error：终止并展示报错

6.4 数据重组阶段

这个 helper 的真正作用不是“发请求”，而是把后端的流式响应重新拼成前端可用的数据结构：

  • delta 逐块追加到同一条 assistant 文本上
  • usage 更新右侧统计面板
  • tool_call / tool_result 写入调试轨迹
  • [DONE] 表示本轮消息已经完整结束
这层的关键价值：把“后端发回来的流”翻译成前端能直接消费的事件，让 UI 可以边生成边展示。

7. 服务端结构：从入口到业务模块

现在的后端已经不是一个大文件硬扛全部逻辑，而是拆成了“启动层 - 路由层 - 业务层 - 统计层”四段。这样做的好处是每一层都只干一件事，调试时也能很快定位问题。

7.1 启动层：server/index.ts

这个文件只负责接线，不负责业务：

  • 读取 .env.local 和 .env
  • 创建 Express 实例并挂载 JSON 中间件
  • 调用 registerRoutes(app)
  • 启动监听并打印当前模式、模型和 API Key 状态

它的定位很明确：把服务拉起来，但不参与聊天流程。

7.2 路由汇总层：server/routes/index.ts

这里相当于总开关，把所有端点集中注册到 Express：

  • /api/usage 由 routes/usage.ts 处理
  • /api/health 由 routes/health.ts 处理
  • /api/rag/chat 由 routes/ragChat.ts 处理
  • /api/chat 由 routes/chat.ts 处理
  • /api/chat/multi 由 routes/chatMulti.ts 处理

7.3 四个核心 HTTP 入口

/api/chat 是单 Agent SSE，主要走 ReAct；/api/chat/multi 是多 Agent SSE，走 Supervisor-Worker 图；/api/rag/chat 是 JSON RAG 流程；/api/usage 和 /api/health 则是观测和调试接口。

这几个入口分开以后，功能边界会非常清楚：聊天、检索、多 Agent、统计、健康检查各走各的路，不会互相缠在一起。

7.4 单 Agent 路径：routes/chat.ts + server/chat.ts + react/runConversation.ts

单 Agent 的实际顺序是：

  1. routes/chat.ts 收到请求，先校验 messages，再挂 SSE 头
  2. 创建 UsageAccumulator，把每次 LLM 调用的用量都记到同一个请求里
  3. 调用 createChatStream()
  4. server/chat.ts 先做 system prompt 组装、上下文裁剪、输入注入检测
  5. 如果没有 API Key 或强制 Mock，就转到假流式输出
  6. 如果是真模型，就进入 runConversation() 的 ReAct 图
  7. 最后把 delta 和 usage 一起通过 SSE 回给前端

7.4.1 单 Agent 的数据组装细节

这里最关键的不是“调用了谁”，而是“调用之前怎么组装输入”。

  • 前端传来的 messages 是整段对话，但服务端不会原样直塞给模型
  • createChatStream() 会先把 systemPrompt 固定加进去
  • 再调用 clipMessages() 把上下文裁到有限长度
  • 最后得到的 clippedMessages 才是真正进入 ReAct 的输入

所以你可以把这层理解成：前端负责拼会话，服务端负责收口成模型能吃的上下文。

7.5 RAG 路径：routes/ragChat.ts + rag/answer.ts

RAG 不是流式聊天，而是“先检索，再回答”的 JSON 接口：

  1. 前端传入 question 和 history
  2. 服务端只保留 user / assistant 历史，system 由后端固定注入
  3. retrieveForAnswer() 先做召回、判空、重排
  4. 如果没命中，直接返回“资料里没有相关内容”，不浪费模型调用
  5. 如果有命中，buildRagPrompt() 组装 prompt，再调一次模型
  6. 最终把 answer、hits、usage 一次性返回

7.5.1 RAG 的 prompt 组装细节

  • retrieveForAnswer() 先拿到原始召回结果
  • 如果判定为空，直接结束，不进入模型
  • 如果有资料，buildRagPrompt() 会把资料块编成 [1] [2] ...
  • 再把固定的 RAG system、历史消息、当前 question 按顺序拼成最终 messages

这一步就是典型的数据组装：检索结果不是直接给模型看，而是先转成 prompt 结构。

7.6 多 Agent 路径：routes/chatMulti.ts + multi-agent/graph.ts

多 Agent 的请求顺序更像任务编排：

  1. 路由层先找最后一条 user 消息
  2. 编译 Supervisor-Worker 图
  3. Supervisor 先决定应该派哪些 Worker
  4. Worker 并行执行自己的工具与 mini ReAct
  5. Aggregate 把多个 Worker 的结果汇总成最终回复
  6. 最后统一写出 delta 和 usage

7.6.1 多 Agent 的数据组装细节

  • Graph 入口只接收最后一条用户消息，不把整段 history 都丢进去
  • Supervisor 的输出会写回 state 里的 routeDecision
  • Worker 的结果写入 workerResults
  • Aggregate 再把这些中间结果组装成最终 finalOutput

所以多 Agent 的核心不是“多问几次模型”，而是把中间态一层层收集起来，再汇成最终答案。

7.7 Token 与观测：usage/accumulator.ts + routes/sse.ts

Token 不是等整个页面结束再算，而是按请求级累加。每次 LLM 调用都会通过 bindUsageCallback() 进入 UsageAccumulator，请求结束时再写入 store 并回传前端。

这意味着你可以很清楚地看到：

  • 一次请求里到底调用了几次模型
  • 单 Agent、RAG、多 Agent 各自的成本差异
  • Mock、空检索、真实 LLM 这几种路径有没有被正确区分

7.8 横切总览：Token / Guard / Trace 分别挂在哪

这份说明书现在按流程图的方式来看，会更准确：横切能力不是单独挂一个总章，而是分散挂到各自模块入口上。

  • /api/chat：UsageAccumulator 记 askModel；detectInjection() 先看输入；validateToolCall() 拦工具；detectLeakage() 护输出；traceChatRequest() / traceAskModel() 走 LangSmith
  • /api/chat/multi：Supervisor / Worker / Aggregate 各自记 usage；Worker 内部用 runToolSafely()；Aggregate 最后再做 detectLeakage()；过程事件走 SSE onTrace，LangSmith 当前不挂包层
  • /api/rag/chat：只记检索命中后的单次 LLM usage；没有工具调用，所以没有 toolGuard；当前也没有 SSE Trace / LangSmith；判空和重排属于检索模块自己的保护逻辑
  • /api/chat/confirm：不新增 token 口径，仍归属父 /api/chat；确认前走输入合法性和流程闸门，确认事件通过 SSE 过程面板展示

所以看文档时，不要再把 Token、Guard、Trace 只理解成“最后一节”。它们更像是每条业务链路都各自挂上的基础设施。

现在这层写法是比较工程化的：入口只接线，流程放业务模块，统计独立处理。文档里如果还写成一个大入口，就会明显过时。

8. ReAct 逻辑：runConversation()

对应流程图：单 Agent ReAct + 横切

ReAct 的本质很简单：先问模型，模型决定要不要调工具；如果调了工具，就把工具结果回填，再问下一轮；直到模型给出最终文字。但在代码里，它不只是一个 while 循环，而是一条带有预检、回填、收敛上限和输出防护的状态图。

8.1 为什么用 LangGraph

以前可以用 for 循环写，现在用 LangGraph 是为了更清楚地表达状态流转：

  • askModel：问一次模型
  • applyTools：执行本轮工具调用
  • reply：把最终回答交给前端

真正跑起来之前，还有一层 prefetchSearchDocsIfEnabled() 的前置判断：如果这轮打开了知识库搜索，它会先检索，检索为空就直接结束，不再进入 ReAct 图。

8.2 状态里保存什么

  • messages：当前消息上下文
  • turn：当前第几轮模型调用
  • toolCalls：模型本轮发出的工具调用
  • assistantContent：模型原始正文
  • assistantReasoningContent：思考模式要回填的 reasoning
  • finalText：是否已经可以结束

这些状态不是摆设。messages 用来保存“模型看见过什么”，turn 用来控制最多问几轮，toolCalls 用来承接模型刚刚要求执行的工具，finalText 用来决定下一步是继续跑工具还是直接回复。

8.3 askModel 节点

它只做一次模型请求，然后根据返回决定下一步：

  • 没有 message：直接返回空文本
  • 没有 tool_calls：模型已经完成回答，走 reply
  • 有 tool_calls：进入 applyTools

这里还有一个收敛阈值：MAX_MODEL_TURNS = 5。如果模型一直调用工具但始终不给最终回答，系统会直接停止，返回“这轮没做完”的固定文案。

8.4 工具执行 applyTools

这里会把 assistant + tool_calls 先写回 messages，再逐个执行工具，最后把 tool 结果作为 role=tool 的消息追加进去。

这样下一轮问模型时，模型能看到“自己刚才请求了什么、工具返回了什么”。

如果工具调用被 guard 拒绝，或者工具本身执行失败，回填到 messages 的仍然是一个可见结果。这样模型下一轮不会“以为工具成功了”，而是能基于失败信息调整回答。

8.5 reply 节点

最终文字回到这里，会先做一次知识库回答风格归一，再做泄露检测，最后才推给前端。也就是说，reply 不是简单吐字，而是最后一道输出整理和防护。

  • searchDocs 打开时，会先走 normalizeKnowledgeAnswer()，把来源清单和冗余格式收掉
  • 再走 detectLeakage()，防止 system prompt 被带出来
  • 最后才通过 onDelta() 把文字送到前端

8.6 ReAct 里的横切点

  • Token：每次 askModel 都会把 usage 记到同一个请求级累加器里，所以一轮 ReAct 可能记多次
  • Guard：输入先走 detectInjection()，工具前走 validateToolCall()，输出再走 detectLeakage()
  • Trace：输入风险、工具过程、输出泄露都会通过 onTrace() 进 SSE；如果开了 LangSmith，再额外生成 chat-request / askModel / tool span
收敛限制：MAX_MODEL_TURNS = 5。如果模型一直想调工具但不结束，就在这里强行停止，避免死循环。

9. RAG 逻辑：先检索，再回答

对应流程图：资料问答 RAG + 横切缺口

RAG 不走聊天工具链，而是单独的问答路径。它的核心原则是：先找资料，再让模型基于资料回答。这条链路里真正重要的不是“问模型回答”，而是“先把可用资料整理好，再让模型只围着资料答”。

9.1 answerFromDocs()

这是 RAG 的总入口，做的事情是：

  1. 清理 question
  2. 调用 retrieveForAnswer() 先做召回、判空、重排
  3. 把命中的资料块和最近几轮 history 拼进 prompt
  4. 如果没有命中，直接返回固定文案，不再调模型
  5. 如果有命中，再调用一次模型生成最终答案

这里有两个关键点经常被忽略：第一，当前问句已经单独作为 question 传入，所以 history 里必须去掉最后一条 user，避免重复；第二，空结果不是“让模型自由发挥”，而是直接短路成固定回复。

9.2 retrieveForAnswer() 到底做了哪三步

真正的 RAG 检索不是一步到位，而是三段式：

  1. 先用 CANDIDATE_K = 20 做向量召回，先多捞一些候选段落
  2. 再用 judgeRetrieval() 判断这批候选能不能算“有资料”
  3. 最后如果重排模型可用，就用 rerankHits() 把前 Top5 重新排序后再注入

这一步的意义是：先保证别漏，再保证别吵，最后再把最相关的内容放进 prompt。

9.3 判空为什么不是只看分数

judgeRetrieval() 不是简单地拿 Top1 分数一刀切，而是有一个“分数 + 标题命中”的双条件：

  • Top1 分数达到 MIN_TOP_SCORE = 0.6，就认为这次可以继续
  • 如果分数没到 0.6，但标题和问题明显对得上，也允许放行
  • 如果两者都不满足，就直接判空，返回 资料里没有相关内容

这样做是为了避免“标题明明对上了，但分数略低却被误杀”的情况，尤其是问文档小节标题时很常见。

9.4 命中结果如何展示

返回给前端的 hits 不只是原始文本，还带这些信息：

  • rank：向量召回排名
  • rerankRank：重排后的排名
  • promptIndex：真正注入 prompt 的顺序
  • score 和 rerankScore：分数对照

这些字段的作用不是“展示好看”，而是让你能看到：哪些结果是召回来的，哪些结果是重排后真正喂给模型的，哪些结果最终没有进 prompt。

9.5 buildRagPrompt() 怎么把资料塞进模型

buildRagPrompt() 做的不是简单拼字符串，而是把固定规则、资料块和历史消息按顺序组装成消息数组：

  1. 先把 RAG_SYSTEM_PROMPT 放进 system
  2. 再把检索命中的资料编成 [1] [2]... 的 evidence blocks
  3. 然后把最近几轮 history 接上，但只保留 user / assistant
  4. 最后把当前 question 作为新的 user 放到末尾

如果 judgment.empty 或 hits.length === 0，它会直接返回 empty: true，调用方不再进模型。这就是为什么 RAG 的“先检索”是真短路，不是形式上的检索。

9.6 为什么要分离 history 和 question

当前问句已经单独作为 question 传入，所以 history 里必须去掉最后一条 user，避免 prompt 重复。

9.7 检索到回答之间到底发生了什么

  1. retrieveForAnswer() 先把问题送去检索，得到 rawHits、判空结果、重排结果
  2. buildRagPrompt() 把固定 RAG system、资料块和最近几轮 history 拼成消息数组
  3. 如果资料为空，buildRagPrompt() 直接返回 empty: true，调用方不再调模型
  4. 如果资料足够，completeRagMessages() 才会真正问模型
  5. 模型返回后，再经过 normalizeKnowledgeAnswer() 做一次输出整理

所以 RAG 的逻辑并不是“向量检索 + 一句回答”，而是召回、判空、重排、注入、生成、归一六步连起来。

9.8 RAG 里的横切点

  • Token：只有检索通过并真正调用 completeRagMessages() 时，才会记这次 LLM usage；判空直接短路，不会产生成本
  • Guard：RAG 不走 detectInjection() / validateToolCall() / detectLeakage() 这套聊天工具链，而是依赖检索判空、固定 system prompt 和资料注入边界
  • Trace：当前没有 SSE Trace / LangSmith span 包层，前端主要通过 hits 面板和 usage 看这条链路是否正常
RAG 的关键不是“能不能答”，而是“能不能说清楚自己依据了什么资料”。

10. 多 Agent 逻辑：Supervisor-Worker

对应流程图：多 Agent + 横切

多 Agent 的目标不是让模型更“聪明”，而是让不同任务交给不同 Worker，职责更清楚。它的真实流程是：Supervisor 先判断要派谁，Worker 再各自干活，最后由 Aggregate 汇总成一段话。

10.1 Supervisor 做什么

Supervisor 只做路由，不做回答。它会根据用户问题判断需要分发给哪个 Worker：

  • realtime：天气、时间等实时数据
  • kb：知识库、笔记、资料搜索
  • general：闲聊兜底

Supervisor 的输出不是自由文本，而是通过 route 工具形成结构化 JSON。只要 LLM 没调工具、工具参数解析失败、或者 worker 名称不合法，都会直接兜底到 general。

10.2 Worker 做什么

Worker 是真正干活的节点。以 RealtimeWorker 为例，它只看天气和时间，不看知识库。

  • 给 Worker 单独的 system prompt
  • 给 Worker 单独的工具白名单
  • Worker 自己做 mini ReAct 循环

每个 Worker 都是一个独立小世界：它只看自己的 task，只能用自己的工具，自己内部也有最大轮次限制。比如 RealtimeWorker 只暴露 getWeather 和 getCurrentTime，KBWorker 只暴露 searchDocs，互相看不到对方工具。

10.3 为什么要隔离工具

工具隔离的价值在于：模型不会乱调不属于自己的工具，边界更稳，调试更容易。

更具体一点说，Worker 真正执行工具前还会再过 runToolSafely()，里面先做 validateToolCall()，只有工具名、参数和 JSON 都合法，才允许执行。这样就算模型幻觉出一个不存在的工具名，也不会真的跑出去。

10.4 Aggregate 怎么收口

Worker 跑完后，结果不会直接原样扔给前端，而是先交给 aggregate() 统一整理：

  • 只有一个成功 Worker 时，直接透传它的输出，少一次 LLM 调用
  • 多个 Worker 时，把各自结果整理成一个多来源上下文，再让模型汇总
  • 如果汇总模型失败，就退回简单拼接，尽量不丢信息
  • 最终输出还会再过一次 detectLeakage()，防止泄露 prompt

10.5 多 Agent 里的横切点

  • Token：Supervisor、Worker、Aggregate 都会各自通过同一个请求级 accumulator 记 usage，最后合并成一条请求成本
  • Guard：Supervisor 只允许 route 白名单；Worker 只允许自己的工具白名单；工具执行前还会过 runToolSafely()；Aggregate 再做一次输出泄露检测
  • Trace：过程事件走 SSE 的 supervisor_route、worker_done、delta；LangSmith 当前不挂在这条图上
你现在的多 Agent 结构，已经不是“把所有东西堆一个 prompt”了，而是把职责拆成了可理解的单元。

11. Token、Tracing、Evals 与安全防护

11.1 Token 统计

Token 统计不是“最后统一算一下”这么简单，而是从单次 LLM 响应一路累到请求结束，再写进前端和本地存储。

11.1.1 第一步：单次 LLM 响应里拿到 usage

模型调用结束后，后端会从响应 JSON 里解析出 usage：

  • server/usage/parseUsage.ts 负责把 prompt_tokens、completion_tokens、total_tokens 转成项目内部的 TokenUsage
  • 如果响应里没有 usage，或者三个值全是 0，就当这次没有有效计数
  • 这一步会在单 Agent、Multi-Agent、RAG 的非流式模型调用里发生

11.1.2 第二步：每次调用都先记到请求级累加器

一次用户请求不一定只调一次模型，所以不能把 token 直接当成“这轮对话的总量”。后端会先把每次 usage 记到 UsageAccumulator：

  • bindUsageCallback() 把 record(model, source, usage) 封装成回调
  • 单 Agent 里，ReAct 每问一次模型就记一次
  • 多 Agent 里，Supervisor、Worker、Aggregate 可能都各自记一次或多次
  • RAG 里如果命中了资料并调了模型，也会记一次；没命中则不会记

11.1.3 第三步：请求结束时合并成一条记录

当本轮请求结束后，服务端不会把每次调用单独写给前端，而是把整个请求合并成一个摘要：

  • mergedUsage() 把所有调用的 prompt / completion / total 相加
  • primaryModel() 选出出现次数最多的 model 作为本轮主模型
  • estimatedCostUsd() 按模型单价估算本轮请求成本
  • toSnapshot() 生成前端展示用的摘要
  • toRecord() 生成写入 store 的完整记录

11.1.4 第四步：写入 SSE 或 JSON，再落盘

不同链路的回传方式不一样，但都走同一套统计逻辑：

  • /api/chat 和 /api/chat/multi 会通过 SSE 的 type: "usage" 事件把摘要回给前端
  • writeUsageToStream() 会把记录写进 data/usage-log.json，然后再推一条 SSE
  • /api/rag/chat 会把 usage 直接放进 JSON 响应里，同时也写入 store

11.1.5 第五步：前端拿到 usage 后更新面板

前端的 streamChat() 和 askRag() 会把服务端回来的 usage 再转成页面状态：

  • src/api/chat.ts 收到 type = usage 后，转成 UsageSnapshot 并回调给 useChat.ts
  • src/api/usage.ts 的 fetchUsageSummary() 会在页面加载和每次用量变化后刷新累计面板
  • useChat.ts 把最新一次请求的 usage 放到 lastUsage
  • 累计统计则来自 /api/usage 的全局汇总

11.1.6 这套流程为什么要这么绕

因为你这里统计的不是“某一次模型调用”，而是“一次用户请求里所有模型调用”的总和。这样才能看清：

  • 一次 ReAct 到底问了几轮模型
  • 多 Agent 的成本是不是明显高于单 Agent
  • RAG 空结果时有没有真的省掉模型费用
  • 不同 model 的成本差异有没有被正确记录

11.2 Tracing

Tracing 不是“顺手记个日志”这么简单，而是把一次对话的内部动作包成一棵可视化的 span 树。它关心的是：请求是怎么进来的、模型问了几轮、工具怎么执行的、哪一步出了问题。

11.2.1 第一步：先决定这次请求要不要上报

  • server/tracing/langsmith.ts 先读 LANGCHAIN_TRACING_V2、LANGSMITH_TRACING_V2 等环境变量
  • 只要其中任一路径为 true，就进入 tracing 模式
  • 没开 tracing 时，代码仍然正常跑，只是不把 span 发到 LangSmith

11.2.2 第二步：整段 ReAct 请求先包成根 span

runConversation() 在最外层会调用 traceChatRequest()：

  • 根 span 名称是 chat-request
  • 它对应一次完整的 /api/chat 请求
  • processInputs 只记最后一条用户问题的摘要，不把整段 messages 全塞进去
  • 这样 LangSmith 列表里能一眼看出这是哪一次问话

11.2.3 第三步：每次 askModel 都再包一层 span

ReAct 里每次问模型，都会进 traceAskModel()：

  • 它包住的是 requestCompletion() 这一层真实 LLM 请求
  • span 的 turn、model、message_count、search_docs 都会记进去
  • 模型有没有发出 tool_calls，也会在输出摘要里显示
  • 这样你能看见到底是第几轮把工具调出来的

11.2.4 第四步：每个工具调用单独成 span

工具不是在模型里“黑箱执行”的，而是由 traceToolRun() 单独包起来：

  • applyToolCalls.ts 调 runToolWithTracing()
  • 如果 tracing 开着，就进 traceToolRun()
  • span 里会记录工具名、参数、是否报错、结果预览
  • 这一步能直接看出：模型到底调用了天气、时间，还是调用错了工具

11.2.5 第五步：LangSmith 里看到的是整棵链路树

最终在 LangSmith 面板里，你会看到的是：

  • 根节点：一次聊天请求
  • 子节点：第 1 轮、第 2 轮、第 3 轮 askModel
  • 孙节点：每次工具执行 span

也就是说，Tracing 真正做的事情是把“模型怎么想、工具怎么跑”拆成可回放的流程，而不是只留一句“调用了某工具”。

11.3 Evals

Evals 不是简单的“跑一遍看看”，而是把固定样本喂给当前实现，再按规则判定这次改动有没有把老行为弄坏。

11.3.1 第一步：先准备数据集

  • 单 Agent 的样本放在 evals/dataset.json
  • 多 Agent 的样本放在 evals/dataset-multi.json
  • 每条样本都包含固定的 messages、开关参数和期望结果

11.3.2 第二步：评测脚本直接调用真实实现

  • scripts/run-evals.ts 直接调用 createChatStream()
  • scripts/run-evals-multi.ts 直接调用 compileMultiAgentGraph()
  • 这意味着 eval 不是测 UI，也不是测 HTTP，而是直接测后端编排逻辑
  • 运行前要求 LLM_API_KEY 可用，且 MOCK_MODE 不能开

11.3.3 第三步：把运行结果收集成可判分数据

每条样本跑完后，脚本会把结果整理成一条 run 记录：

  • 单 Agent 记录 output、tools、error
  • 多 Agent 记录 output、routedWorkers、tools、error
  • 这些结果都来自真实执行过程，不是人工填的答案

11.3.4 第四步：用规则判分，不让模型自己判自己

  • 单 Agent 用 evals/evaluators.ts 判 toolsInclude、toolsExclude、mustNotMatch
  • 多 Agent 还会额外判 routeIncludes、routeExcludes
  • 判分结果只看 pass / fail，不让另一个模型来当裁判

11.3.5 第五步：输出 pass / fail 和失败原因

脚本最后会打印每条样本的结果：

  • 通过就显示 PASS
  • 失败就列出原因，比如工具缺失、路由不对、输出命中禁则
  • 还会附上工具路径和输出预览，方便你回头定位是哪一步坏了

所以 Evals 的真正作用是：把“这次改动有没有回退”变成可重复检查的流程，而不是靠手动聊天碰运气。

11.4 防护层

防护层不是独立的一块“安全模块”，而是分布在请求生命周期的几个关键关口：输入进来先看一遍，工具执行前再看一遍，模型输出前再看一遍，知识库搜索也有自己的兜底。这样做的目标是：把危险拦在不同阶段，而不是等最后才统一补救。

11.4.1 第一道：输入层检测

用户消息刚进 server/chat.ts 时，系统会先看最后一条 user 有没有明显的注入意图：

  • detectInjection() 只做风险标记，不直接改写用户输入
  • 命中 high / medium 后，会通过 injection_detected 事件告诉前端
  • 这样 UI 能知道这一轮为什么被标高风险，但对话还可以继续正常跑
  • 它的作用更像“先打标签”，不是“直接拦截全部可疑输入”

11.4.2 第二道：知识库搜索前的判空与降级

如果用户勾了“搜索知识库”，prefetchSearchDocsIfEnabled() 会在第一轮 askModel 之前先去检索：

  • 先拿最后一条 user 当 question
  • 把检索结果写入本轮 system，而不是伪造一条 assistant 回复
  • 如果检索出错或资料为空，直接返回 empty: true，让 runConversation() 用固定文案结束
  • 这一步的目的，是避免模型在“没资料”的时候继续硬编文档名、章节号和引用

11.4.3 第三道：工具调用前的白名单校验

模型决定要调工具之后，还不能直接执行，必须先过 validateToolCall()：

  • 先检查工具名是否在白名单里，防止模型幻觉出不存在的函数
  • 再检查参数长度，防止超长 payload 注入
  • 最后验证参数是不是合法 JSON
  • 如果任何一项失败，就直接回填 { error }，不真正执行工具

11.4.4 第四道：工具执行时的连续失败兜底

即便工具名和参数都合法，也不代表它一定要一直跑下去。applyToolCalls() 里还有一层连续失败控制：

  • 同一个工具如果连续失败，ConsecutiveFailureTracker 会记住
  • 达到阈值后，后续相同工具不再真的执行，而是直接回填停止说明
  • 这样能避免模型死磕一个一直失败的工具，拖着整轮对话不结束

11.4.5 第五道：输出层泄露检测

当模型准备把最终答案交给前端时，还会再过一遍 detectLeakage()：

  • 它会在输出里找 system prompt 的关键指纹
  • 如果命中多个关键短语，就判定为泄露
  • 这时不会把原文直接给前端，而是替换成安全文案
  • 同时还会发出 output_leak_blocked 事件，方便前端和 tracing 一起观察

11.4.6 这几道防护合在一起的顺序

  1. 用户输入先经过注入检测
  2. 如果开了知识库，再先做检索判空
  3. 模型决定调工具后，再做工具白名单和参数校验
  4. 工具执行如果一直失败，就启用连续失败兜底
  5. 模型最终输出前，再做一次泄露检测

所以这节的核心不是“有几个安全点”，而是每一层各自挡什么、挡在流程的哪个位置。这样你看代码时，就不会把它们混成一个抽象的安全概念。

11.4.7 多 Agent 的防护链路

多 Agent 不是“把多个模型并在一起”这么简单，它同样有自己的防护链路，而且和单 Agent 的防护思路一致：先路由，再执行，再汇总，每一层都有限制。

  1. 用户问题先进入 Supervisor，由它判断应该交给哪些 Worker。
  2. supervisorRoute() 会强制模型通过 route 工具输出结构化结果；如果 LLM 调用失败、没有调用工具、JSON 解析失败、或者 worker 名称不在白名单里，都会兜底到 general。
  3. 真正执行任务时，每个 Worker 只能使用自己的工具白名单：realtime 只能查天气和时间，kb 只能搜知识库，general 不带工具，互相不能越权。
  4. Worker 真正调用工具前，还会再过一层 runToolSafely()。这里会先跑 validateToolCall()，检查工具名、参数长度和 JSON 合法性，拒绝后只回填 { error }，不会真的执行。
  5. 每个 Worker 内部都有自己的 mini-ReAct 循环，但都带最大轮次限制。以 realtimeWorker 和 kbWorker 为例，最多只跑 3 轮，避免模型一直卡在“继续想一想”的循环里。
  6. 所有 Worker 执行完以后，aggregate() 会先整理各个结果，再决定是直接透传还是调用模型汇总。这里不是简单拼接，而是把多源信息重新组织成一段连贯回答。
  7. 最终输出在返回前还会再过一遍 detectLeakage()。如果汇总结果里碰到 system prompt 或 Worker prompt 的泄露痕迹，就会被替换成安全文案，不直接暴露给前端。
  8. 如果汇总模型本身失败，aggregate() 也不会直接断掉，而是退回到简单拼接，保证信息尽量不断。

所以多 Agent 的防护不是额外挂一个“安全开关”，而是把路由、工具、执行轮次、汇总输出这四个位置都卡住。这样即使某一层出问题，整条链路也不会失控。

12. 一次完整请求的执行顺序

下面是最常见的普通聊天流程，从用户点发送到最终消息显示：

用户输入
  → useChat.send()
    → 追加 user message
    → 普通聊天：runStream()
      → streamChat()
        → POST /api/chat 或 /api/chat/multi
          → server/index.ts
            → registerRoutes(app)
              → routes/chat.ts 或 routes/chatMulti.ts
                → createChatStream() / compileMultiAgentGraph()
                  → 裁剪上下文、检测注入、决定 Mock/API
                  → 单 Agent：runConversation()
                    → askModel → applyTools → askModel → reply
                  → 多 Agent：supervisor → workers → aggregate
                  → SSE 逐段回传 delta / tool trace / usage
        → 前端把 delta 拼到 assistant 占位消息
      → 完成后保留最终消息

RAG 请求则是另一条路：
  → useChat.send()
    → runRag()
    → POST /api/rag/chat
      → routes/ragChat.ts
        → answerFromDocs()
          → retrieveForAnswer()
          → 空结果：直接返回固定文案
          → 有结果：buildRagPrompt() + completeRagMessages()
        → JSON 返回 answer / hits / usage

13. 一些设计上的判断

  • 普通聊天、RAG、多 Agent 分成不同入口，是合理的，能减少互相污染
  • 前端只做展示和状态管理，后端做编排和安全约束，是合理的职责划分
  • 知识库检索和工具调用不要混成一条链路，否则调试会很痛苦
  • 上下文裁剪、system prompt 固定、空结果兜底，这三层对稳定性很关键
总体来看，这套实现已经不是“能跑”而已，而是已经具备一套相当完整的 AI 应用工程样板。

14. 按文件逐个讲解

这一章不再讲整体概念，而是按文件拆开，告诉你每个文件到底负责什么、输入是什么、输出是什么、和谁对接。

14.1 src/composables/useChat.ts

这是前端的状态中枢。页面上所有和聊天有关的动作，最后都会落到这个文件里。

  • 维护 messages、model、ragMode、searchKb、error、toolTrace、lastUsage
  • send() 负责把用户输入变成一轮完整会话
  • runStream() 负责普通聊天的流式请求
  • runRag() 负责资料问答的 JSON 请求
  • retry()、stop()、clear()、setRagMode() 负责会话控制

它的输入是 UI 状态和用户输入，输出是已经组织好的消息列表和请求动作。你可以把它理解成“前端聊天控制台”。

14.2 src/api/chat.ts

这是前端网络层，专门负责和后端的 SSE 接口对接。

  • streamChat() 负责 POST 请求和 SSE 解析
  • 把服务端返回的 delta 拼回 assistant 文本
  • 把 usage 转成前端统计面板能显示的数据
  • 把 tool_call / tool_result 转成调试轨迹
  • fetchHealth() 负责探测后端当前模式

它的核心价值不是“发请求”，而是把流式事件转换成前端状态变化。

14.3 server/index.ts

这是后端启动入口，职责很轻。

  • 加载环境变量
  • 创建 Express 实例
  • 挂 JSON 中间件
  • 注册所有路由
  • 启动监听并打印运行模式

它不做业务编排，只负责把服务拉起来。读这个文件时，重点看“接线”，不要期待这里有具体聊天逻辑。

14.4 server/routes/index.ts

这是路由汇总层，作用很单纯：统一把各个 endpoint 挂到 Express 上。

  • 挂载 /api/usage
  • 挂载 /api/health
  • 挂载 /api/rag/chat
  • 挂载 /api/chat
  • 挂载 /api/chat/multi

14.5 server/routes/chat.ts

这是单 Agent 聊天入口，负责把普通聊天请求送进 ReAct 主链路。

  • 校验请求体里的 messages
  • 设置 SSE 响应头
  • 创建请求级 UsageAccumulator
  • 调用 createChatStream()
  • 把 delta、trace、usage 写回前端

14.6 server/chat.ts

这个文件是单 Agent 的前置整理层，负责把模型真正要吃的数据收口。

  • 拼装固定的 system prompt
  • 根据 searchDocs 决定是否加知识库提示
  • 做输入注入检测
  • 调用 clipMessages() 裁剪上下文
  • 在 Mock / API 两条路径之间分流

14.7 server/react/runConversation.ts

这是 ReAct 的主编排文件，真正实现“问模型 -> 调工具 -> 再问模型”的循环。

  • askModel 问一次模型
  • applyTools 执行模型请求的工具
  • reply 把最终文字交给前端
  • 用 MAX_MODEL_TURNS 控制循环上限

14.8 server/rag/answer.ts

这是 RAG 的问答入口，负责把检索和回答串成一条清晰链路。

  • 调用 retrieveForAnswer()
  • 把召回结果转成可展示的 hits
  • 判空时直接返回固定文案
  • 命中时调用 completeRagMessages()
  • 最后输出 answer、hits、usage

14.9 server/rag/prompt.ts 与 server/rag/retrieve.ts

这两个文件一个管 prompt，一个管检索。

  • retrieve.ts 负责向量召回、判空、重排
  • prompt.ts 负责把资料块和历史消息组进 RAG prompt
  • 两者合起来，才构成“先找资料，再让模型回答”

14.10 server/multi-agent/graph.ts

这是多 Agent 的主图文件，负责把 Supervisor、Worker 和 Aggregate 串起来。

  • Supervisor 先做路由决策，把用户问题分发给合适的 Worker
  • Worker 在自己的能力边界内并行执行，结果写回图状态
  • Aggregate 接收所有 Worker 的结果，整合为最终回复
  • 整个过程通过图状态对象传递中间态，便于统一记录 token 和调试日志

这一层本身不负责具体安全判断，但它把 supervisorRoute()、各个 Worker 和 aggregate() 串成了一条固定顺序的链路，防护逻辑就分散在这三个节点里分别完成。

14.11 server/usage/accumulator.ts

这个文件负责请求级 Token 累加。

  • 接收每次 LLM 调用的 usage
  • 合并 prompt / completion / total
  • 估算成本
  • 生成前端可展示的 usage 摘要

14.12 server/routes/sse.ts 与 server/routes/usage.ts

前者负责 SSE 输出格式，后者负责 Token 记录的读写接口。

  • setSseHeaders() 让浏览器按流处理响应
  • writeUsageToStream() 把 Token 统计写回 SSE
  • /api/usage 让你能查看累计记录，必要时也能清空

14.13 server/tools/*

工具目录负责把天气、时间、知识库检索等能力包装成模型可以调用的工具。

  • 定义工具 schema
  • 执行工具逻辑
  • 把工具注册进模型调用链

14.14 server/guard/* 与 server/tracing/*

这两类文件分别负责安全和观测。

  • guard 处理输入注入、输出泄露
  • tracing 处理请求链路追踪
