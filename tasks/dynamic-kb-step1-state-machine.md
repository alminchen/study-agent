# 动态知识库 · 步骤 1：两条链路与任务状态机

> 对应 `dynamic-kb-execution-plan.md` 步骤 1。本步只写概念、不写代码。
> 产出三样资产：两条链路图、任务状态定义、「分类 vs 文档 vs 块」概念区分。

## 1. 为什么必须先画链路

动态知识库的难点不在单个功能，而在**时序与归属**：

- **时序**：上传发生在用户点击的瞬间；切片和向量化却要花几秒到几十秒。提问随时会来，
  而库里可能正有另一篇在写。如果不把「接收」和「处理」拆开，上传接口会被 embed 拖死，
  提问还会撞见写到一半的脏数据。
- **归属**：一块向量必须能回答三个问题——它属于哪个**分类**（决定搜哪里）、属于哪篇
  **文档**（决定替换哪一批）、是文档里的第几**块**（决定展示和引用）。
  归属不清，删除会留幽灵、重复上传会混版。

先把这两件事画对，后面写代码只是照着填空。

## 2. 两条链路

### 链路 A：上传（写）—— 只负责「接收」，不负责「处理」

```text
用户选择 .md 文件 + 选定分类
        │
        ▼
  POST /api/kb/upload（接口入口）
  ├─ 校验：类型 .md / 大小 ≤1MB / 非空
  ├─ 落盘原件（data/uploads/<docId>/）
  ├─ 建任务记录（status=queued）
  └─ 立即返回「已接收，处理中」        ← 不在这里切片、不在这里 embed
        │
        ▼
  后台任务循环（worker，独立于请求线程）
  ├─ 取 queued → 置 chunking → 切片 → 置 chunked
  ├─ 取 chunked → 置 embedding → 向量化 → 置 searchable
  └─ 任一步失败 → 置 failed，记 stage（read / chunk / embed）
```

### 链路 B：提问（读）—— 永远只读「已完成」的数据

```text
用户输入问题 + 当前分类
        │
        ▼
  POST /api/kb/search（接口入口，和上传完全分开）
  ├─ 只读两类数据：categories、searchable 状态的向量块
  ├─ 检索层硬过滤：where category=当前分类
  ├─ 用同一套 embed() 编码问题
  ├─ 余弦相似度 TopK
  └─ 返回块（带分类/文档/来源），不碰进行中的半成品
```

### 两条链路在代码入口上分离的意义

- 上传请求**永不等待** embed，耗时不随文件大小和库规模增长。
- 提问请求**永不写入**，不会和入库的「先删旧再写新」打架。
- 某一篇正在入库时，提问照常返回，只是搜不到那篇的未完成块——这正是
  「入库中提问不阻塞」的验收来源。

## 3. 任务状态机

### 状态流转图

```text
                ┌──────────────────────────────────┐
                │                                  │
                ▼                                  │ 重试（从失败层续跑）
 queued ──► chunking ──► chunked ──► embedding ──► searchable
    │          │                │
    │          ▼                ▼
    └──► failed（stage=read）  failed（stage=chunk）  failed（stage=embed）
```

### 各状态含义（谁推进、卡住意味着什么）

| 状态 | 含义 | 谁推进 | 卡住时排查 |
| --- | --- | --- | --- |
| `queued` | 原件已落盘，任务已入表，等待后台取活 | 上传接口写入 | 任务没被 worker 捞走 → worker 没起 / 轮询崩了 |
| `chunking` | 正在读原件 + 切块 | worker | 长时间停在 `chunking` → 读文件卡死或 worker 死循环 |
| `chunked` | 块已落库可预览，等待向量化 | worker | ——（中间态，供「预览块」使用） |
| `embedding` | 正在逐批向量化 + 写库 | worker | 长时间停在 `embedding` → embed 服务卡死 |
| `searchable` | 块已入库，提问可命中 | worker | —— |
| `failed` | 某一步失败，已停止 | worker | 看 `stage` 定位是哪一层 |

### 失败必须记录「停在哪一层」

任务记录里 `stage` 只允许三个值，对应三类根因：

| stage | 失败现场 | 典型原因 | 重试动作 |
| --- | --- | --- | --- |
| `read` | 读落盘原件失败 | 文件被删 / 权限 / 磁盘异常 | 重新入队，从读文件续跑 |
| `chunk` | 切块失败 | 空文件 / 全是垃圾块 / 无任何有效块 | 重新入队，从切块续跑 |
| `embed` | 向量化或写库失败 | ONNX 模型加载失败 / 维度异常 / 写盘失败 | 重新入队，从向量化续跑 |

重试规则：**只复位任务状态、保留 docId**，从失败那一层接着跑，不重复制造文档 id、
不整篇重建。这是步骤 7 的实现依据。

### 替换语义（状态机之外的硬规则）

同一文档再次上传 = 新的任务，但 `docId` 与旧任务相同。入库写到
`searchable` 前，先执行「删掉该 `分类 + docId` 的旧块，再写新块」。
于是：

- 库里该文档的块数永远等于最新一版，新旧两版不混住。
- 提问只读 `searchable`，所以「先删后写」期间提问碰不到空窗——删旧发生在
  这个文档自己的任务走到 embedding 时，而提问按分类扫的是已完成的块。

## 4. 分类 vs 文档 vs 块

| 维度 | 是什么 | 回答的问题 | 错误做法 |
| --- | --- | --- | --- |
| 分类（collection） | 检索作用域，如「规范」「日记」 | 搜哪里？硬边界 | 做成装饰标签、检索仍扫全库 |
| 文档（doc） | 一次上传的一篇原始资料 | 替换哪一批？删除清谁？ | 用文件名当身份（重命名就断链） |
| 块（chunk） | 可独立阅读的检索单元 | 命中哪段？引用来源？ | 把整篇塞进提问 prompt |

三者关系：

```text
categories
  └─ 一个分类下有多篇文档
        └─ 一篇文档被切成多个块（docId 相同，chunkId 递增）
              └─ 每个块记录：category + docId + source + chunkId + embedding
```

每块记录必须带齐这四元组，缺一个就回答不了上述任一问题。
