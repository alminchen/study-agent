架构总览

先建立全局地图：浏览器只持有展示状态；Express 持有 Key、system、工具环、检索与横切。下面是真实调用链，不是概念口号。

三条链路（端到端）

A. 单 Agent · POST /api/chat
App → useChat.send → runStream → streamChat → routes/chat（SSE + ConfirmSession + Accumulator） → createChatStream → clipMessages + detectInjection → runConversation（askModel ↔ applyToolCalls → reply） → writeUsageToStream → [DONE]
  1. 前端只传 user/assistant；system 在 createChatStream 注入。
  2. ReAct 可能多次 askModel；每次 usage 进同一 Accumulator（source=askModel）。
  3. 需确认工具：SSE pending_confirm → 前端 POST /api/chat/confirm → 原 SSE 继续。
一条用户消息 ≠ 一次 LLM：必须请求级累加 Token，才能解释成本。
B. 多 Agent · POST /api/chat/multi
streamChat(multiAgent:true) → chatMulti：injection + Accumulator + compileMultiAgentGraph.invoke → supervisorRoute → Worker(s)（runToolSafely）→ aggregate（detectLeakage） → usage + [DONE]
  1. 选路只看 multiAgent，与 searchDocs 无关。
  2. Token source 分桶：supervisor / worker / aggregate。
  3. invoke 中途 writeSse，否则确认事件推不出去。
与单 Agent 共用工具 methods 与 ConfirmSession 语义，避免两套确认协议。
C. 资料问答 · POST /api/rag/chat
runRag → askRag（SSE） → ragChat：injection → Accumulator(rag) → traceRagRequest? → answerFromDocs：toolGuard(searchDocs) → retrieve → prompt → LLM → outputGuard → rag_meta + delta + usage + [DONE]
  1. 独立 system（RAG_SYSTEM_PROMPT），不带天气工具 schema。
  2. 判空可不调模型 → Accumulator 为空 → 不写 usage。
  3. hits 走 rag_meta；正文走 delta，复用气泡拼字逻辑。
RAG 也曾返回 JSON；改 SSE 后才能与 chat 共用 ToolTracePanel 学横切。

硬边界（读代码前先记住）

  • UI history 无 system；发给模型的 system 只在服务端。
  • 确认接口不解耦成「第二次聊天」；仍挂在原 SSE 的 wait 上。
  • SSE Trace（用户）≠ LangSmith（开发者）。
  • 注释红线：改逻辑时保留教学注释，只增补不删。
  • 验收脚本：见 Code/scripts（RAG 逐步测试 + eval:chat/multi），比只点 UI 更可靠。
