09 · 多 Agent server/multi-agent/

Supervisor 路由 → 一个或多个 Worker（各自 mini ReAct）→ Aggregate 汇总。 与单 Agent 共用工具实现、ConfirmSession、toolCallGuard / outputGuard 语义，但编排与确认挂载点不同。

模块地图与真实调用链

入口 POST /api/chat/multi（routes/chatMulti.ts） → new ConfirmSession() + UsageAccumulator + writeSse/onTrace → compileMultiAgentGraph(options).invoke(state) → 中途 SSE：supervisor_route / pending_confirm / worker_done … → 整图结束后 delta + usage + [DONE] → finally confirmSession.dispose()
图内 START → supervisorNode（supervisorRoute） → workersNode（Promise.all + getWorkerFn） → aggregateNode（aggregate + detectLeakage） → END
确认必须在 graph.invoke 进行中 经 onTrace 推 SSE：若等整图结束再推， runToolSafely 里 await wait 时前端永远收不到 pending_confirm。 因此 Session / Trace / writeSse 走编译期闭包，不进 LangGraph State。

graph.ts

MultiAgentGraphOptions
interface · 编译时注入，不进 State
字段类型作用
accumulator?UsageAccumulator请求级 Token 累加；各节点 onUsage(source)
defaultModel?stringusage 记录默认模型名
confirmSession?ConfirmSession未传则需确认工具安全降级
onTrace?ToolTraceHandlertool_call / pending_confirm / confirm_resolved …
writeSse?(payload) => voidmulti 专有：supervisor_route / worker_done
forceKbSearch?boolean前端勾选搜索知识库：Supervisor 后若无 kb 则 ensureKbWorker 强制追加
State 只放可序列化业务字段；跨请求确认与 SSE 写出口是请求级副作用，闭包注入更干净。searchDocs 勾选与选路 endpoint 解耦，但会驱动 forceKbSearch。
compileMultiAgentGraph(options?)
→ CompiledGraph（可 invoke）

注册三个节点并线性连边；按 source 绑定 bindUsageCallback(acc, source, defaultModel)。

  1. supervisorNode：调用 supervisorRoute；若 forceKbSearch 则 ensureKbWorker；writeSse({ type:"supervisor_route", workers, forceKbSearch })，返回 { routeDecision }。
  2. workersNode：对 decision.workers Promise.all；getWorkerFn 缺失则造 error 结果；每个 Worker 完成后立刻 worker_done；返回 { workerResults }。
  3. aggregateNode：调用 aggregate，返回 { finalOutput }。
State 字段：userMessage / apiKey / baseUrl / model / signal（入口只读）· routeDecision（supervisor 写）· workerResults（workers 写）· finalOutput（aggregate 写）
不用条件边拆多个 Worker 节点：JS 侧并行不如 node 内 Promise.all；Worker 数量 1~N 动态，条件边要枚举组合不实际。三节点线性图更易教、易 Trace。

supervisor.ts

WorkerName
"realtime" | "kb" | "action" | "general"

白名单：路由解析后非法 name 会被滤掉。

RouteDecision
{ workers: { name: WorkerName; task: string }[] }

每个 Worker 拿到的是 Supervisor 拆出的 子任务，不是整段用户原文（除非兜底 general）。

supervisorRoute(options)
→ Promise<RouteDecision>
参数说明
userMessage本轮用户原文
apiKey / baseUrl? / model?透传 LLM 配置
signal?断开 / 超时 abort
onUsage?Token；图里绑 source="supervisor"
  1. callLLM：system = 路由提示；tools = 伪工具 route；toolChoice: "auto"（DeepSeek thinking 不能强制 tool_choice 函数名）。
  2. 失败 / 无 tool_calls / JSON 坏 / 过滤后空 → fallback(task) → 仅 general。
  3. 成功：解析第一个 tool_call 的 arguments → 白名单 filter → 返回。
用 Function Calling 输出结构化路由，比自由文本正则稳；Supervisor 只分发不回答，避免把业务逻辑塞进路由层。多层兜底保证图永远能往下走。

llm.ts

CallLLMOptions / CallLLMResult

统一非流式 chat/completions 入参与简化出参（ok、status、content、toolCalls、usage）。

callLLM(options)
→ Promise<CallLLMResult>
  1. 拼 baseUrl / model 默认值；body 含 messages，可选 tools + tool_choice。
  2. fetch(.../chat/completions)，非 2xx → ok:false 不抛。
  3. parseUsageFromResponse → 可选 onUsage。
  4. 抽出 message.content 与 tool_calls。
与 react/complete.ts 分开：multi 无 thinking 流式/ reasoning_content 回填需求；supervisor/worker/aggregate 共用薄封装，避免复制粘贴 headers。

runToolSafely.ts

runToolSafely(name, rawArguments, options)
→ Promise<unknown>
参数说明
name工具函数名
rawArguments模型给的 JSON 字符串
options.toolCallId与 confirm API 对齐的键
options.confirmSession?人工确认会话
options.onTrace?过程事件
options.signal?wait 可被 abort
  1. 尝试 JSON.parse → onTrace(tool_call)。
  2. validateToolCall；拒绝则 tool_result.error 返回，不执行。
  3. findTool；未知工具 → error。
  4. 若 isToolRequiringConfirm：无 Session → 降级 error；有则 pending_confirm → await wait → confirm_resolved → allow 才 tool.run，deny 回填拒绝。
  5. 普通工具直接 run；最后一律 onTrace(tool_result)。
多 Agent 不走 applyToolCalls，但确认/Guard 必须同语义，故抽「安全执行」共用路径。Guard 在确认之前：非法调用不必打扰用户。

aggregate.ts

aggregate(options)
→ Promise<string>
参数说明
results全部 WorkerResult
userMessage用户原问，作汇总上下文
apiKey / baseUrl? / model? / signal?LLM
onUsage?图里 source="aggregate"
  1. 单 Worker 且 !error → 直接 guardFinalOutput(output)（省一次 LLM）。
  2. 否则 formatWorkerResults 拼进 user 消息，callLLM 整合。
  3. LLM 失败或空 content → fallbackConcat 再 guard。
  4. guardFinalOutput = detectLeakage，泄露则换 safeText。
Aggregate 不是字符串 join：多来源要自然语言连贯。单路透传省成本；最终必过 outputGuard，防 Worker/Aggregate system 指纹泄露。

workers/realtimeWorker.ts

runRealtimeWorker(ctx)
工具隔离：仅 getWeather + getCurrentTime · MAX_TURNS=3
  1. messages = system（天气/时间边界）+ user(task)。
  2. 循环：callLLM 带工具 → 无 tool_calls 则返回 content；有则 runToolSafely 回填 role:tool。
  3. 超轮次 → error「查询超时」。
模型看不到 searchDocs，自然不会越界检索；「今天天气」可同时调时间+天气。

workers/kbWorker.ts

runKBWorker(ctx)
仅 searchDocs · 底层仍是 retrieveForAnswer（与单 Agent prefetch 同管线，控制流不同）
  1. 同 realtime 的 mini ReAct 骨架。
  2. prompt 强制先检索、标 [n]、无结果不编造。
多 Agent 下 KB 是按需 Worker；单 Agent 的 prefetch 是「开关强制先搜」。同一 executeSearchDocs，两种编排。

workers/actionWorker.ts

runActionWorker(ctx)
仅 draft_message · 经 runToolSafely 挂确认闸门
  1. 模型应调 draft_message；wait 期间 SSE pending_confirm。
  2. 用户 allow/deny 后继续循环，用一句话汇报模拟发送或拒绝。
有后果动作与闲聊 Worker 隔离，确认路径清晰；不把确认逻辑塞进 general。

workers/generalWorker.ts

runGeneralWorker(ctx)
无工具 · 单次 callLLM

失败返回 error 结果；成功返回 content。toolsCalled 恒为 []。

最简兜底：不循环、不工具，避免不确定意图误调天气/检索。
