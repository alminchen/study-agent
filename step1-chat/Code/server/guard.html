step1-chat · Code RAG Guard Usage useChat 横切对照

11 · Guard server/guard/

三道门横切片：输入只标记风险、工具可拒绝执行、输出可替换泄露文本。 与业务编排解耦，单 Agent / 多 Agent / RAG 三条链路复用同一套函数。 前端通过 SSE（injection_detected、tool_result.error、output_leak_blocked）在 Trace 面板看见防护过程。

挂载点速查

  • Input：createChatStream（chat.ts）· chatMulti · ragChat → detectInjection
  • Tool：applyToolCalls · runToolSafely · answerFromDocs（校验 searchDocs）→ validateToolCall
  • Output：单 Agent reply · multi aggregate · RAG answerFromDocs → detectLeakage

server/guard/inputGuard.ts

RiskLevel / GuardResult / Rule（类型）
type RiskLevel = "none" | "medium" | "high"
interface GuardResult { level; matchedRules: string[] }
interface Rule { id; level: "medium"|"high"; pattern: RegExp }

做什么：约定检测结果形状与规则表项。level 取命中规则中的最高档；matchedRules 列出所有命中的规则 id，便于调试与 SSE 展示。

  1. none：未命中任何规则。
  2. medium：仅可疑话术（可能误杀正常讨论）。
  3. high：明确注入意图（忽略指令、越狱、索要 system prompt 等）。
结果结构化后，路由层可统一发 injection_detected，而把「是否硬拒绝」留给后续策略——教学仓库默认不切断，便于观察全链路。
RULES（模块常量）
const RULES: Rule[] — high 组 + medium 组正则

做什么：用轻量正则表达常见 Prompt Injection 话术，无外部依赖、不调模型。

  1. HIGH：ignore_instructions（中/英）、new_role、output_system_prompt、dan_jailbreak。
  2. MEDIUM：role_play_request、base64_extract、developer_mode。
  3. 每条规则有稳定 id，命中后进入 matchedRules，便于 Trace「命中了哪条」。
教学阶段用规则引擎足够演示「输入层防护」概念；上生产再换分类器/策略引擎时，可保留 GuardResult 契约不变。
detectInjection
export function detectInjection(input: string): GuardResult

做什么：扫描用户输入文本，返回最高风险等级与全部命中规则 id。不修改、不拦截输入本身——调用方自行决定放行 / 降级 / 拒绝。

  1. 初始化 matchedRules=[]，level="none"。
  2. 遍历 RULES：pattern.test(input) 则 push rule.id。
  3. 若规则为 high → level="high"；否则仅当当前不是 high 时升为 medium。
  4. 返回 { level, matchedRules }（可同时命中多条）。
方向名称说明
入参input用户原文（chat 末条 user / rag question 等）
出参GuardResultlevel + matchedRules
上下游： 调用方 — server/chat.ts（createChatStream）、routes/chatMulti.ts、routes/ragChat.ts。 命中后通常 SSE 推 injection_detected → 前端 onTrace → ToolTracePanel。 本函数不调用其它模块。
只标记不拦截：教学上先看见风险事件与后续链路是否仍执行；一刀切断会导致学员无法观察 ReAct/RAG。真正硬拦截可在学完后再在路由层加策略。

server/guard/toolCallGuard.ts

ALLOWED_TOOLS / MAX_ARGUMENTS_LENGTH
Set("getWeather","getCurrentTime","searchDocs","draft_message") · MAX_ARGUMENTS_LENGTH = 2048

做什么：定义工具名白名单与参数字符串长度上限。模型幻觉出不存在的工具名、或注入超长 payload 时，在执行前被拒绝。

  1. 白名单与项目真实注册工具对齐；新增工具必须同步改此处。
  2. 2048 字符上限针对 arguments 原始字符串（不是美化后的 JSON）。
工具执行有副作用（查天气、写草稿、检索）；执行前闸门比「跑起来再炸」更安全，也给模型一条可回填的 error 文案以改道。
ToolCallGuardResult
interface ToolCallGuardResult { allowed: boolean; reason?: string }

做什么：校验结果。allowed=false 时 reason 供 applyToolCalls / runToolSafely 回填给模型或推 SSE tool_result.error。

把「拒绝原因」结构化，前端/模型都能读到同一句话，排障不用翻服务端日志。
validateToolCall
export function validateToolCall(name: string, rawArguments: string): ToolCallGuardResult

做什么：在真正执行工具之前，校验单个 tool_call：白名单 → 长度 → JSON 可解析。快速、无副作用。

  1. 若 name 不在 ALLOWED_TOOLS → { allowed:false, reason: 工具「x」不在白名单… }。
  2. 若 rawArguments.length > 2048 → 拒绝（疑似注入超长 payload）。
  3. 尝试 JSON.parse(rawArguments)；失败 → 拒绝「不是合法 JSON」。
  4. 全部通过 → { allowed:true }（不返回解析后的对象，调用方自行再 parse）。
方向名称说明
入参name模型返回的函数名
入参rawArguments模型返回的 arguments 字符串
出参ToolCallGuardResult是否允许 + 可选原因
上下游： react/applyToolCalls.ts（单 Agent）· multi-agent/runToolSafely.ts（多 Agent）· rag/answer.ts（对 searchDocs 做同语义校验，拒绝则不检索不调模型）。 不调用其它 Guard。
三处共用同一函数，保证「聊天工具」与「RAG 内部检索」对白名单语义一致，Trace 面板也能显示同一工具名 searchDocs。

server/guard/outputGuard.ts

FINGERPRINTS / LEAK_THRESHOLD / REPLACEMENT
FINGERPRINTS: string[] · LEAK_THRESHOLD = 2 · REPLACEMENT = 固定安全文案

做什么：从各链路 system prompt 中抽取关键短语作为指纹。模型回复若同时包含多个指纹，判定为泄露 system 内容，替换为安全回复。

  1. 指纹覆盖：单 Agent chat system、多 Agent Worker/Aggregate system、RAG system（rag/prompt.ts）。
  2. 阈值 = 2：命中 ≥2 个片段才判泄露，降低单句误杀。
  3. REPLACEMENT 为固定中文道歉 + 引导提问，不回显任何指纹原文。
防「把 system 原文复述给用户」。指纹库增补时只增不删，避免旧 system 句式仍可能被模型吐出却漏检。
OutputGuardResult
interface OutputGuardResult { leaked: boolean; safeText: string; matchedFingerprints: string[] }

做什么：统一输出层结果。leaked=true 时 safeText 为替换文案；否则 safeText 为原文。matchedFingerprints 无论是否泄露都带回，便于 SSE 与调试。

调用方只需写 const text = guard.safeText，不必自己分支拼替换句；Trace 仍能展示命中了哪些指纹。
detectLeakage
export function detectLeakage(output: string): OutputGuardResult

做什么：检测模型最终回复是否泄露 system prompt 内容。使用简单 includes 匹配指纹；达到阈值则替换。

  1. 遍历 FINGERPRINTS，若 output.includes(fp) 则记入 matched。
  2. 若 matched.length ≥ LEAK_THRESHOLD(2) → 返回 leaked=true、safeText=REPLACEMENT、matchedFingerprints=matched。
  3. 否则 leaked=false、safeText=原文、仍返回已命中的（可能 0 或 1 个）指纹列表。
方向名称说明
入参output规范化后的模型回复文本
出参OutputGuardResult是否泄露、应用文本、命中指纹
上下游： react/runConversation.ts（单 Agent 最终 reply）· multi-agent/aggregate.ts（汇总输出）· rag/answer.ts（normalize 之后）。 泄露时路由可再推 SSE output_leak_blocked → 前端 Trace。
输出层是最后一道门：即使用户注入成功骗模型「复述规则」，用户侧仍看不到完整 system。阈值 2 在召回与误杀之间取教学友好折中。

三道门如何配合

  1. 输入：看见攻击意图 → Trace 亮红，但默认继续跑，方便对照「标记 vs 拦截」。
  2. 工具：挡住幻觉工具名与脏参数 → 回填 error，模型可改口，不会真执行。
  3. 输出：挡住 system 原文外泄 → 用户只看到安全替换句，同时 Trace 记录指纹命中。
分层比「一个大拦截器」更清晰：每层职责单一，三条业务链路可以按需挂载，不必 fork 三份防护代码。
