12 · Token / Usage server/usage/

请求级 Token 累加与成本估算。核心事实：用户发 1 条消息 ≠ 只调 1 次 LLM。 单 Agent ReAct 可能 askModel 多轮；多 Agent 含 Supervisor / Worker / Aggregate；RAG 通常 0 或 1 次。 本目录负责解析 API usage → 请求内累加 → 单价估算 → 落盘汇总；前端经 SSE usage 事件与 GET /api/usage 展示。

典型挂载（路由层）：创建 UsageAccumulator → bindUsageCallback 传给 complete/callLLM → 请求结束 writeUsageToStream（见 routes/sse）推 SSE 并 appendUsageRecord。

server/usage/types.ts

数据分层：单次 LLM 原始用量 → 一次 HTTP 请求摘要 → 持久化记录 → 全局汇总。类型本身无运行时逻辑，但是所有模块的契约。

TokenUsage
interface TokenUsage { promptTokens: number; completionTokens: number; totalTokens: number }

做什么：描述单次 LLM 调用的用量，对应 OpenAI 兼容响应里的 usage 字段（经 parseUsage 转成 camelCase）。

  1. promptTokens：输入侧（system + 历史 + 工具回填等）。
  2. completionTokens：模型生成侧。
  3. totalTokens：通常为二者之和；部分平台不返回 total 时由解析层相加。
上下游：parseUsageFromResponse 产出 → Accumulator.record 消费 → pricing.estimateCostUsd / mergeUsage。
先固定「单次调用」原子单位，才能在请求级做相加与按模型估价，而不会把 ReAct 多轮误当成一次调用。
UsageRecord
interface UsageRecord { id; timestamp; endpoint; model; promptTokens; completionTokens; totalTokens; llmCalls; estimatedCostUsd }

做什么：写入 store 的请求级完整记录。一次用户提问（一条 HTTP）对应一条，即使内部调了多次 LLM 也合并为一条。

字段说明
idusage_{timestamp}_{random}
endpoint"chat" | "chat/multi" | "rag/chat"
model主模型名（出现次数最多；无调用用请求默认）
llmCalls本次请求内有效 LLM 次数
estimatedCostUsd按单价表估算，非真实账单
前端「累计」与「最近记录」需要可持久化的行；把多轮 LLM 压成一行，对用户心智是「这次提问花了多少」，而不是「第 3 次 askModel 花了多少」。
UsageSummary
interface UsageSummary { totalRequests; total*Tokens; totalCostUsd; byEndpoint; byModel; recent }

做什么：GET /api/usage 返回的全局汇总结构：总量 + 按 endpoint/model 分组 + 最近记录倒序切片。

  1. byEndpoint / byModel：各含 requests、totalTokens、costUsd。
  2. recent：原始 UsageRecord 列表（store 默认最多 50 条展示）。
上下游：getUsageSummary 生成 → 前端 fetchUsageSummary → UsagePanel。
分组字段让学员对比「multi 是否比单 Agent 更贵」「某模型是否更耗 token」，而不是只看一个总数字。
UsageSnapshot
interface UsageSnapshot { endpoint; model; promptTokens; completionTokens; totalTokens; llmCalls; estimatedCostUsd }

做什么：推给前端 SSE / JSON 的单次请求摘要。字段与 Record 相近，但不含 id / timestamp（展示用即时面板）。

  1. 由 Accumulator.toSnapshot(endpoint, fallbackModel) 生成。
  2. 经 writeUsageToStream 写成 type:"usage" 事件；前端 onUsage 写入 lastUsage。
SSE 事件应轻量；持久化身份（id/时间）只在落盘时需要，不必每次打字流里携带。

server/usage/parseUsage.ts

parseUsageFromResponse
export function parseUsageFromResponse(data: unknown): TokenUsage | null

做什么：从 chat/completions 非流式响应 JSON 中提取 usage，规范化为 TokenUsage。缺失或全 0 返回 null，调用方跳过 record。

  1. 校验 data 为对象；取 data.usage，非对象则 null。
  2. 读 snake_case：prompt_tokens / completion_tokens / total_tokens，用 Number 转数字，缺省 0。
  3. 若无 total_tokens，用 prompt+completion 相加。
  4. 三者皆 ≤0 视为无效（Mock 或异常）→ null。
  5. 否则返回 camelCase TokenUsage。
方向名称说明
入参datafetch 后 JSON.parse 的完整响应
出参TokenUsage | null有效用量或跳过标记
上下游：调用方包括 react/complete.ts、multi-agent/llm.ts、rag/complete.ts。不处理 stream:true（流式通常无完整 usage）。
各 LLM 封装层统一解析，避免 prompt_tokens 字段名差异散落；Mock 返回 null 后 Accumulator 自然跳过，空请求不会污染账本。

server/usage/pricing.ts

MODEL_PRICING / DEFAULT_PRICING（模块常量）
Record<modelId, { inputPer1M; outputPer1M }> · DEFAULT = { 0.2, 0.8 }

做什么：手工维护各模型「美元 / 百万 token」单价表；未知模型走偏保守的默认价，避免低估。

  1. 表中含 deepseek-chat、deepseek-v4-flash、gpt-5.4-mini、gpt-5.6-sol 等学习 demo 近似价。
  2. 新模型需手动加一行；不以平台实时价 API 为准。
本模块只做估算教学，不是财务系统。不考虑缓存命中、套餐价、thinking token 单独计费。
estimateCostUsd
export function estimateCostUsd(model: string, usage: TokenUsage): number

做什么：按模型单价估算单次 LLM 调用的美元成本。

  1. 查 MODEL_PRICING[model]，没有则 DEFAULT_PRICING。
  2. inputCost = promptTokens/1e6 × inputPer1M。
  3. outputCost = completionTokens/1e6 × outputPer1M。
  4. 返回二者之和。
方向名称说明
入参model本次调用 model id
入参usage该次 TokenUsage
出参number估算 USD
上下游：UsageAccumulator.estimatedCostUsd 对每次 entry 调用后相加。
按「每次调用」估价再求和，才能正确处理同一请求内混用不同 model 的情况；若先 merge token 再乘单一单价会算错。
mergeUsage
export function mergeUsage(usages: TokenUsage[]): TokenUsage

做什么：把多次 TokenUsage 的 prompt/completion/total 简单相加，得到请求级合并用量。

  1. reduce 初始全 0。
  2. 逐字段累加返回新对象。
上下游：Accumulator.mergedUsage()。
合并逻辑单独成函数，便于单测「三轮 ReAct token 是否相加正确」，也不和估价逻辑缠在一起。
formatCostUsd
export function formatCostUsd(cost: number): string

做什么：把成本格式化为前端可读美元字符串。极小非零值显示 <$0.000001，避免全零误导。

  1. cost===0 → "$0"。
  2. 0 < cost < 1e-6 → "<$0.000001"。
  3. 否则 $${cost.toFixed(6)}。
短对话成本常低于百分之一美分；直接 toFixed 成 $0.000000 会让学员以为「没计费」。

server/usage/accumulator.ts

UsageSource（类型）
type UsageSource = "askModel" | "supervisor" | "worker" | "aggregate" | "rag"

做什么：标记每次 LLM 调用来自哪一层，便于调试分析（当前未直接暴露给前端面板，但写入 entries 供后续扩展）。

多 Agent 一次提问可能 5+ 次 LLM；没有 source 标签就无法解释「钱花在 Supervisor 还是 Worker」。
class UsageAccumulator
class UsageAccumulator { record; get llmCalls; get isEmpty; mergedUsage; primaryModel; estimatedCostUsd; toSnapshot; toRecord }

做什么：单次 HTTP 请求内的 Token 累加器。每个 API 入口 new 一个实例；请求结束 toSnapshot / toRecord。

  1. 内部 entries: { model, source, usage }[]。
  2. 生命周期：路由创建 → 各 LLM 层 record → 结束写 SSE + store。
上下游：chat / chatMulti / ragChat 路由持有实例；complete/callLLM 经 bindUsageCallback 写入。
请求级实例避免全局可变状态串台；一次提问一条账，符合用户心智。
UsageAccumulator.record
record(model: string, source: UsageSource, usage: TokenUsage | null | undefined): void

做什么：记录一次有效 LLM 调用。null/undefined 或 totalTokens≤0 时跳过（Mock、失败、空响应）。

  1. 守卫：无 usage 或 total≤0 → return。
  2. push 一条 { model, source, usage }。
跳过无效条目，保证 llmCalls 与合并 token 只反映真实计费调用。
get llmCalls / get isEmpty
get llmCalls(): number · get isEmpty(): boolean

做什么：llmCalls 返回 entries.length；isEmpty 表示没有任何有效 LLM 调用（例如 RAG 检索判空不调模型、纯 Mock）。

  1. 只读访问内部数组长度，无副作用。
路由层可据此决定是否仍推 usage 事件或如何展示「0 token」；语义比直接暴露 entries 更清晰。
mergedUsage
mergedUsage(): TokenUsage

做什么：把所有 entry 的 usage 交给 mergeUsage，得到请求级合计 token。

上下游：toSnapshot 使用。
展示用「总计」字段，不要求前端自己加。
primaryModel
primaryModel(fallback: string): string

做什么：取出现次数最多的 model 作为「主模型名」；无 entries 时返回 fallback（请求参数里的 defaultModel）。

  1. 空 → fallback。
  2. 用 Map 计每个 model 出现次数。
  3. 遍历取 count 最大者；平局保留先扫到的最大值逻辑。
多 Agent 可能同 model 多次；面板需要一个简洁的「本次用了哪个模型」标签，而不是列出全部。
estimatedCostUsd
estimatedCostUsd(): number

做什么：对每次 entry 分别 estimateCostUsd 后求和。

  1. reduce 累加 estimateCostUsd(e.model, e.usage)。
见 pricing：必须按次估价，不能先 merge 再乘价。
toSnapshot
toSnapshot(endpoint: UsageRecord["endpoint"], fallbackModel: string): UsageSnapshot

做什么：生成前端 SSE 用摘要：合并 token、主模型、llmCalls、估算成本，不含 id/timestamp。

  1. merged = mergedUsage()。
  2. 组装 UsageSnapshot 字段并返回。
上下游：writeUsageToStream / toRecord 内部。
同一套数字既推 SSE 又落盘，避免两处手写字段不一致。
toRecord
toRecord(endpoint, fallbackModel): UsageRecord

做什么：在 snapshot 基础上加 id 与 timestamp，供 store 持久化。

  1. 调用 toSnapshot。
  2. id = usage_${Date.now()}_${random}；timestamp = Date.now()。
  3. 展开 snapshot 字段返回完整 UsageRecord。
id 带随机后缀避免同毫秒并发撞车；时间戳供 recent 倒序与排障。
UsageCallback / bindUsageCallback
type UsageCallback = (usage: TokenUsage, model: string) => void
bindUsageCallback(accumulator, source, defaultModel): UsageCallback

做什么：把 Accumulator 绑定成可直接传给 complete.ts / callLLM 的 onUsage 回调；source 与 defaultModel 闭包固定。

  1. 返回函数 (usage, model) => accumulator.record(model || defaultModel, source, usage)。
  2. model 为空时用 defaultModel，避免写入空字符串。
方向名称说明
入参accumulator当前请求实例
入参sourceaskModel / supervisor / worker / aggregate / rag
入参defaultModel兜底模型名
出参UsageCallback可注入 LLM 层
上下游：路由创建多个 bind（例如 supervisor 与 worker 不同 source）→ 各 LLM 封装在拿到 parseUsage 结果后调用。
闭包固定 source，避免每次 callLLM 忘传标签；接口形状与现有 onUsage 对齐，改动面最小。

server/usage/store.ts

存储策略（学习 demo）：内存数组 + data/usage-log.json 双写；最多 500 条；GET recent 最多 50 条。生产应换 Redis/时序库。

loadFromDisk（内部）
function loadFromDisk(): UsageRecord[]

做什么：进程启动时读 JSON；文件不存在或解析失败返回空数组，保证服务能起来。

  1. existsSync(LOG_FILE) 否 → []。
  2. readFileSync + JSON.parse；非数组 → []。
  3. catch → []。
用量日志损坏不应阻断聊天主路径；宁可空账本，不可启动崩溃。
persist（内部）
function persist(): void

做什么：把当前 records 写回磁盘；必要时创建 data/ 目录。

  1. 目录不存在则 mkdirSync recursive。
  2. writeFileSync pretty JSON（缩进 2）。
pretty 打印方便学员打开文件肉眼看账；demo 体量下性能可接受。
appendUsageRecord
export function appendUsageRecord(record: UsageRecord): void

做什么：追加一条请求级用量；超过 MAX_RECORDS(500) 时截断最旧的，然后 persist。

  1. records = [...records, record]。
  2. 若 length > 500，slice(-500)。
  3. persist()。
上下游：writeUsageToStream（及路由结束路径）调用。
硬上限防止 JSON 无限膨胀撑爆磁盘；环形保留最近记录对教学足够。
clearUsageRecords
export function clearUsageRecords(): void

做什么：清空内存与磁盘日志（DELETE /api/usage）。

  1. records = []；persist() 写出空数组。
上下游：DELETE 路由 → 前端 clearUsageHistory。
demo 一键清账，方便对比实验前后成本。
getUsageSummary
export function getUsageSummary(): UsageSummary

做什么：遍历全部 records，计算总量、按 endpoint/model 聚合，并返回最近 MAX_RECENT(50) 条倒序记录。

  1. 初始化 byEndpoint / byModel 空对象与各 total 计数。
  2. 对每条 record：累加 prompt/completion/total/cost；按 endpoint、model 递增 requests/tokens/cost。
  3. recent = reverse(records).slice(0, 50)。
  4. 组装 UsageSummary 返回。
上下游：GET /api/usage → 前端 UsagePanel 累计区。
汇总在服务端做，前端只渲染；避免把完整 500 条都下发后再分组。
