scripts / evals 测试与验收

仓库里没有把 RAG / Agent 验收塞进前端点点点；关键能力靠 scripts/ 命令行脚本 + evals/ 固定数据集回归。 学习顺序建议：先跑通 RAG 流水线脚本（切分→向量→入库→检索→判空→重排→prompt→ask）， 再跑 eval:chat / eval:multi。

为何单独 scripts，而不是只写单元测试框架？

  • 很多验收依赖本机模型文件（BGE / reranker）与 my_notes.json，CLI 更直观。
  • 逐步脚本对应学习计划阶段：每步失败能精确定位（是 embed 坏了还是闸门阈值问题）。
  • eval 走真实 createChatStream / compileMultiAgentGraph，测的是集成行为，不是 mock 壳。

命令行参数（必看）

用 npm run 往脚本传参时，必须加 --，否则参数会被 npm 吃掉：

✅ npm run rag:ask -- "你的问题" ✅ npm run eval:chat -- --id time-now ❌ npm run rag:ask "你的问题"　← 问句到不了脚本

rag:search "问题"（argv 拼接） 必填 npm run rag:search -- "不要把整篇文档塞进 prompt 冒充 RAG"
rag:preview-prompt "问题" 必填 npm run rag:preview-prompt -- "今天北京适合出门吗？"
rag:ask "问题" 必填 npm run rag:ask -- "不要把整篇文档塞进 prompt 冒充 RAG"

推荐学习 / 验收顺序

predawn:bge → rag:preview-chunks → rag:test-embed → rag:ingest（含入库自测）→ rag:test-store → rag:test-retrieve → rag:test-empty → predawn:rerank → rag:test-rerank → rag:test-prompt / preview-prompt → rag:ask → eval:chat / eval:multi · mcp:ping

一、RAG 流水线脚本

predawn-bge.sh · npm run predawn:bge
bash scripts/predawn-bge.sh

做什么

  1. 预下载本地 embedding 模型（bge-large-zh 等），供 server/rag/embedding.ts 使用。
  2. 不跑业务逻辑；失败则后续 test-embed / ingest 都会挂。
把「模型文件就位」与「业务自测」拆开，避免第一次跑 ingest 时又下模型又验逻辑，日志缠在一起。
predawn-rerank.sh · npm run predawn:rerank
bash scripts/predawn-rerank.sh

做什么

  1. 预下载交叉编码器重排模型，供 rerank.ts / test-rerank。
重排是可选项；未下载时 retrieve 会降级 slice，应用不崩，但 test-rerank 会主动 exit(1) 要求先 predawn。
preview-chunks.ts · npm run rag:preview-chunks
npm run rag:preview-chunks npm run rag:preview-chunks -- docs-sample/stage3-rag-notes.md # 等价：npx tsx scripts/preview-chunks.ts [markdown路径]

做什么

  1. 读 Markdown（默认 docs-sample/stage3-rag-notes.md）。
  2. 调用 chunkMarkdown，打印每块 id / title / 字数 / 前 30 字。
  3. 附带人工自测清单（能否单块读懂、标题是否被拆开、交界句是否覆盖）。
参数必填说明
markdown路径否process.argv[2]；缺省样例笔记；相对仓库根目录解析
下游：chunker · 不上游向量库（纯预览）
入库前先肉眼看切分质量；切坏了再 embed 会浪费时间且难排查。
test-embed.ts · npm run rag:test-embed
tsx scripts/test-embed.ts → 断言或 throw

做什么

  1. embed 四句：同句两次、近义、无关。
  2. 断言维度 = EMBED_DIM。
  3. 同句余弦 ≥ 0.99；近义分 > 无关分。
先证明「向量空间有语义结构」，再谈入库检索；否则 TopK 乱了不知道是模型问题还是切分问题。
ingest.ts · npm run rag:ingest
npm run rag:ingest npm run rag:ingest -- path/to/notes.md

做什么

  1. 读 md → chunkMarkdown（缺省 docs-sample/stage3-rag-notes.md）。
  2. 按 BATCH=8 调 embed，组成 StoredChunk[]。
  3. LocalVectorStore.load → replaceSource（同名 source 覆盖不叠加）→ save。
  4. 入库自测 1：文档原句检索，Top1 应够高。
  5. 入库自测 2：资料外问句 Top1 应低于 MIN_TOP_SCORE。
参数必填说明
markdown路径否process.argv[2]；source 名取文件 basename
下游：chunker → embed → vectorStore · 自测内嵌 search
ingest 不只「写文件」，还带两条黄金用例，防止「入库成功但向量全乱」静默通过。
test-store.ts · npm run rag:test-store
先 ingest，再 tsx scripts/test-store.ts

做什么

  1. load 后库非空；每条有 id/source/title/text/seq/embedding 且维度正确。
  2. save → 再 load，条数不变（持久化往返）。
  3. replaceSource 同名不叠成两份。
与 ingest 解耦：不重算 embedding，专测磁盘格式与 API 契约，跑得快。
test-retrieve.ts · npm run rag:test-retrieve
tsx scripts/test-retrieve.ts · 只调 retrieve，不问 LLM

做什么

  1. 直接命中：贴原文问法，目标 chunk-28 须进 Top5。
  2. 近义问法：相关 chunk-16/20 至少其一进 Top5。
  3. 资料外：Top1 分数不得虚高（< MIN_TOP_SCORE）。
  4. 累计 failed，非 0 则非零退出。
召回质量是 RAG 地基；不调聊天模型，避免把「模型胡说」和「检索没命中」混为一谈。
test-empty.ts · npm run rag:test-empty
tsx scripts/test-empty.ts · 测 retrieveForAnswer 闸门

做什么

  1. 有资料问句 → empty=false，hits 非空。
  2. 资料外 → empty=true，hits 清空，但 rawHits 仍保留供调试；topScore 低于门槛。
「有名次 ≠ 有资料」。闸门错了会把噪声塞进 prompt；rawHits 保留是为了面板/脚本对照。
test-rerank.ts · npm run rag:test-rerank
需 predawn:rerank + ingest

做什么

  1. rerankerReady() 否则 exit(1)。
  2. retrieveForAnswer 近义问句；打印向量前 5 vs 重排后注入列表。
  3. 断言注入条数 = DEFAULT_TOP_K；顺序变了打 PASS，不变打 NOTE（库小可能发生）。
证明交叉编码器链路通了；不强求每条问句都改序，避免 brittle 测试。
search.ts · npm run rag:search
npm run rag:search -- "你的问题" # 无参数会打印用法并 exit(1)

做什么

  1. 把 argv.slice(2) 拼成问句（可含空格，请用引号包住）。
  2. 调用 retrieveForAnswer，打印 candidateK / injectK / empty / Top1。
  3. 列出向量候选与（若有）重排注入结果。
参数必填说明
"问题"是空则报错退出；多词用引号：-- "A B C"
交互式探测检索，不是断言脚本；改阈值/问句时先用它肉眼看。
test-prompt.ts · npm run rag:test-prompt
纯单元：假 hits，不碰向量库 / LLM

做什么

  1. 空 judgment → buildRagPrompt 必须 empty、messages 为空。
  2. 有 hits → system 含 RAG_SYSTEM_PROMPT 与编号资料；history 条数裁剪正确。
  3. 校验 formatEvidenceBlocks 编号格式。
prompt 拼装错误会导致「检索对了但模型看不到资料」；用假数据测拼装，与检索解耦。
preview-prompt.ts · npm run rag:preview-prompt
npm run rag:preview-prompt -- "不要把整篇文档塞进 prompt 冒充 RAG" npm run rag:preview-prompt -- "今天北京适合出门吗？" # 无参数 → 打印用法 exit(1)

做什么

  1. CLI 问句（必填）+ 内置 demo history（证明 history 与 question 分离）。
  2. retrieveForAnswer → buildRagPrompt → 打印 roles/内容预览；不调 LLM。
参数必填说明
"问题"是当前问句；历史写死在脚本里作演示
在烧 Token 前先看「模型到底会收到什么」。
ask.ts · npm run rag:ask
npm run rag:ask -- "不要把整篇文档塞进 prompt 冒充 RAG" # 需要 LLM_API_KEY；无问句 → exit(1)

做什么

  1. 读 .env，直接调 answerFromDocs(question)（与 HTTP 同核心，不经 Express）。
  2. 打印 empty / calledModel / topScore / hits 注入标记 / 最终 answer。
参数必填说明
"问题"是argv.slice(2).join(" ")
环境变量要LLM_API_KEY；勿开 MOCK_MODE=1
下游：server/rag/answer.ts（含 toolGuard / outputGuard）
绕过前端/SSE 排错：确认是 RAG 核心问题还是路由/前端问题。

二、Agent 回归评测（evals + scripts）

数据与判分器在 evals/，跑法在 scripts/run-evals*.ts。

文件作用
evals/dataset.json单 Agent 用例（messages、expect 工具/文案规则）
evals/dataset-multi.json多 Agent 用例（期望路由 workers、工具）
evals/types.tsEvalExample / EvalRunResult 等类型
evals/evaluators.tsevaluateRun：规则判分（工具是否调用、输出是否匹配）
run-evals.ts · npm run eval:chat
npm run eval:chat npm run eval:chat -- --id time-now npm run eval:chat -- --id weather-gz --id mars-temp

做什么

  1. 校验有 LLM_API_KEY 且非 MOCK_MODE=1（否则工具假跑，结果不可信）。
  2. 加载 evals/dataset.json；若传入 --id，只跑匹配的 examples（可重复多个 --id）。
  3. 对每条：createChatStream（forceMock:false），收集 onDelta 全文与 onTrace 的 tool_call 名。
  4. evaluateRun(run, example.expect) 判 PASS/FAIL；汇总 passed/total，全过 exit 0。
参数必填说明
--id <caseId>否过滤用例；可写多次。id 见上方「eval:chat 可用 id」表。未传则跑全集。
环境要真 Key；建议 LANGCHAIN_TRACING_V2=false 省额度
下游：server/chat.createChatStream → ReAct 全链路
固定问句 + 规则判分，防止「手测时碰巧对、改完静默回归」。测的是真链路不是 mock。
run-evals-multi.ts · npm run eval:multi
npm run eval:multi npm run eval:multi -- --id multi-weather-only

做什么

  1. 加载 dataset-multi.json；同样支持 --id 过滤。
  2. compileMultiAgentGraph().invoke(...)，从 state 取 routedWorkers、toolsCalled、finalOutput。
  3. 按期望校验路由是否派到正确 Worker、工具是否调用；打印 PASS/FAIL。
参数必填说明
--id <caseId>否如 multi-kb-only；id 见上方 multi 列表
环境要真 Key；禁止 MOCK
下游：multi-agent/graph（不经 Express SSE）
与单 Agent eval 拆开：测的是 Supervisor 路由与 Worker 工具，不是 ReAct 循环细节。

三、MCP 与其它工具脚本

mcp-ping.ts · npm run mcp:ping
stdio 拉起 server/mcp/stdio.ts，listTools + 各调一次

做什么

  1. StdioClientTransport 起 MCP 子进程。
  2. 列出工具名；调用 getCurrentTime、getWeather(广州)。
  3. 证明现有 tools/methods 能被标准 MCP 协议调用（不经聊天页）。
把「工人层可复用」验成可运行事实，而不是只写在注释里。
render-seq-svg.mjs / gen-seq-diagrams.mjs / seq-data.mjs
npm run diagrams · diagrams:ascii

做什么

  1. 根据序列数据生成/渲染文档用时序图（SVG 或 ASCII），服务 docs 流程说明。
图与代码分离维护；改流程时重跑脚本，而不是手改巨大 SVG。
