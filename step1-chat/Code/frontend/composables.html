03 · useChat src/composables/

前端唯一聊天状态中枢（Vue composable）。负责 messages / 流式标志 / ToolTrace / Usage / 模式开关； 按 ragMode 把发送分到普通对话（runStream → streamChat）或资料问答（runRag → askRag）。 两边共用 runSseSession 骨架。不负责拼 system、跑 ReAct、检索或计 Token——那些都在服务端。

阅读顺序建议：历史键与 loadHistory → useChat 初始化与 watch → runSseSession → runStream / runRag → send / retry / stop / clear → resolveToolConfirm → 各 setter。

src/composables/useChat.ts

模块级常量与 id

HISTORY_KEY / RAG_HISTORY_KEY / MODEL_KEY / …
const HISTORY_KEY = "step1-chat:history" · RAG_HISTORY_KEY · MODEL_KEY · RAG_MODE_KEY · SEARCH_KB_KEY · MULTI_AGENT_KEY

做什么：为 localStorage 约定稳定键名。普通对话与资料问答各有独立历史键；模型、RAG 开关、知识库检索开关、多 Agent 开关各自持久化，刷新页面后恢复用户上次选择。

  1. HISTORY_KEY / RAG_HISTORY_KEY：两套消息数组，切换模式互不污染。
  2. MULTI_AGENT_KEY：缺省视为多 Agent（只有显式存过 "0" 才是单 Agent）。
  3. SEARCH_KB_KEY 与 multi 独立——勾选「搜索知识库」不会隐式改 endpoint。
键名带项目前缀，避免与同域其它 demo 冲突；开关拆开存储，防止学员把「开搜索」误当成「走 multi」。
createId
() => `msg_${Date.now()}_${idCounter++}`

做什么：为每条 ChatMessage 生成前端本地 id，供列表 key、占位气泡 patch、不可变更新定位使用。不与服务端会话 id 对齐。

  1. 读取闭包内递增计数器，拼上当前毫秒时间戳。
  2. 保证同毫秒内连续造多条消息也不会撞 id。
上下游：被 send（user 气泡）、runSseSession（assistant 占位）调用；组件侧用 id 做 v-for key。
纯前端 id 足够驱动 UI 更新；若强行等服务端回执再插气泡，流式首包会晚一拍、体验变差。

历史读写辅助（模块内私有）

loadHistory
loadHistory(key: string): ChatMessage[]

做什么：从 localStorage 反序列化历史消息，并对旧版 RAG 字段做兼容补全，避免缺字段导致面板渲染异常。

  1. localStorage.getItem(key)；无数据则返回空数组。
  2. JSON.parse；若不是数组则返回 []。
  3. 对每条消息：若无 rag 原样返回；若有，则补齐 question（缺省空串）以及每个 hit 的 rerankRank / rerankScore（缺省 null）。
  4. 任意异常（坏 JSON、配额等）吞掉并返回 []，保证应用能启动。
方向名称类型 / 说明
入参keylocalStorage 键，通常来自 historyKey(ragMode)
出参ChatMessage[]可直接赋给 messages ref；坏数据时为空数组
上下游：useChat 初始化、setRagMode 切换时调用。不写盘。
教学仓库会演进字段（例如增加 rerank）。兼容读比「清用户历史」更友好；写路径仍由 watch / persist 写出完整新结构。
historyKey
historyKey(ragMode: boolean): string

做什么：按当前是否资料问答模式，返回应对应的 localStorage 键。

  1. ragMode === true → RAG_HISTORY_KEY。
  2. 否则 → HISTORY_KEY。
方向名称说明
入参ragMode是否资料问答
出参string两个常量键之一
上下游：loadHistory、persist、watch、clear、setRagMode 都经此函数取键，避免到处硬编码字符串。
单点映射：以后若再加第三种会话类型，只改这一处即可。

导出：useChat()

useChat
export function useChat(): { messages, model, ragMode, …, send, retry, stop, clear, … }

做什么：创建并绑定一整套聊天会话状态与操作方法。App / 顶栏 / 气泡区 / Trace / Usage 面板都应消费同一份返回值，而不是各自再 fetch。

  1. 从 localStorage 恢复 ragMode、searchKb、multiAgent（默认 multi）、model、messages。
  2. 初始化 isStreaming、error、toolTrace、lastUsage、usageSummary、serverMode。
  3. onMounted：拉 health 与 usage 汇总。
  4. 注册 watch：非流式时把当前模式历史落盘。
  5. 返回 refs + 公开方法（见下文各节）。
上下游：被 App.vue 调用；内部依赖 chat / rag / usage API。
Composable 集中状态，避免「气泡一份 Trace、面板另一份 Trace」的双源真相；教学上也能一眼看见「前端只做会话壳」。
refreshUsageSummary（内部）
async function refreshUsageSummary(): Promise<void>

做什么：请求服务端累计用量，写入 usageSummary，供 UsagePanel「累计」区块展示。

  1. 调用 fetchUsageSummary()（GET /api/usage）。
  2. 无论成功与否，把返回值（可能为 null）赋给 usageSummary。
上下游：onMounted、runSseSession 的 onUsage 回调触发。对应服务端 getUsageSummary。
单次请求的 Token 靠 SSE usage 事件即时展示；累计需要跨请求持久化，故另拉汇总接口，避免前端自己再算一遍账。
watch([messages, isStreaming, ragMode])
watch(..., () => { if (!isStreaming) localStorage.setItem(historyKey(...), JSON.stringify(messages)) })

做什么：在消息或模式变化且当前不在流式中时，把当前模式对应的历史写入 localStorage。

  1. 任一依赖变化触发回调。
  2. 若 isStreaming 为 true，直接跳过（半成品气泡不落盘）。
  3. 否则 setItem(historyKey(ragMode), stringify(messages))。
流式过程中每来一个 delta 都会改 messages；若边流边写盘，刷新会留下残缺助手气泡。等流结束后再持久化更稳。
persistCurrentHistory
function persistCurrentHistory(): void

做什么：立即把当前模式历史写盘，不关心 streaming 标志。用于切换模式前「先落当前会话」、以及 send 落 user 后立刻固化。

  1. localStorage.setItem(historyKey(ragMode.value), JSON.stringify(messages.value))。
上下游：send、setRagMode 调用；与 watch 互补（watch 防半成品，本函数强制落完整快照）。
切模式时必须先存再载，否则旧模式未写盘就被 messages 覆盖成另一条历史。

核心骨架：runSseSession

runSseSession
async function runSseSession(history: ChatMessage[], options: { emptyErrorFallback: string; start: (ctx) => Promise<boolean> }): Promise<void>

做什么：普通对话与资料问答共用的 SSE 会话外壳。负责开流、插占位助手气泡、注入统一回调、以及中止/失败时的文案收尾。真正选哪个 endpoint、拼什么 body，全部交给 options.start。

  1. 开流：新建 AbortController，赋给模块级 abortController；置 isStreaming=true，清空 error / toolTrace / lastUsage。
  2. 占位：createId() 造空 content 的 assistant，拼进 history 后写入 messages。
  3. patchLatest：闭包内不可变更新该 assistant（按 id map 替换），供 onDelta / onRagMeta 使用。
  4. 调用 start：传入 signal、patchLatest，以及四个统一回调——
    • onDelta：拼接正文（流式打字）。
    • onTrace：追加过程步骤；若 kind 为 confirm_resolved，只改对应 pending 行的 status，不追加新行。
    • onUsage：写 lastUsage 并 refreshUsageSummary。
    • onError：写顶栏/气泡用的 error 字符串。
  5. 收尾：清 abort 引用、关 streaming；若用户 abort 且正文仍空 →「已停止生成。」；若未完成且非 abort 且正文空 → 用 error 或 emptyErrorFallback 填气泡；最后把 latest 写回 messages。
方向名称说明
入参history已含本轮 user（及之前消息）的完整列表
入参emptyErrorFallback失败且无 error 文案时的兜底气泡字
入参start具体 API 启动器，返回是否「正常跑完」
出参—副作用更新 refs；无返回值
上下游：仅被 runStream / runRag 调用。start 内再调 streamChat 或 askRag。stop() 通过 abort 打断同一 controller。
chat 与 rag 都改成 SSE 后外壳同构；抽公共函数避免两套「占位 / 中止 / 空泡」逻辑漂移。差异只留在 start 闭包里（endpoint、rag_meta）。

链路适配：runStream / runRag

runStream
async function runStream(history: ChatMessage[], selectedModel: string): Promise<void>

做什么：普通对话入口。把历史压成 {role, content}[]，带上当前模型、searchDocs、multiAgent，交给 streamChat；endpoint 由 multiAgent 决定，searchDocs 只进 body。

  1. 调用 runSseSession(history, { emptyErrorFallback: "请求失败，请重试。", start })。
  2. start 内调用 streamChat({ messages, model, signal, searchDocs, multiAgent, onDelta, onTrace, onUsage, onError })。
  3. multiAgent true → POST /api/chat/multi；false → /api/chat（由 api 层选路）。
方向名称说明
入参history含本轮 user 的完整 ChatMessage 列表
入参selectedModel当前模型 id
上下游：send / retry 在非 RAG 时调用 → streamChat → 服务端 chat / multi 路由。
选路字段显式传入，避免「有 searchDocs 就隐式 multi」。教学上能独立演示「单 Agent + 开搜索」与「多 Agent + 不开搜索」。
runRag
async function runRag(history: ChatMessage[], selectedModel: string): Promise<void>

做什么：资料问答入口。从 history 倒找最后一条 user 作为 question；把「去掉末条 user」的 prior 作为 history 传给后端；SSE 过程事件进 Trace，命中元数据进 message.rag，答案走 delta。

  1. 提取 question（末条 user 的 trim 内容）。
  2. prior = history.slice(0, -1) 再 map 成 role/content，避免 prompt 重复当前问句。
  3. runSseSession，fallback「资料问答失败。」。
  4. start 调 askRag；额外提供 onRagMeta：用 patchLatest 写入 empty / calledModel / topScore / question / hits。
上下游：send / retry 在 ragMode 时调用 → askRag → /api/rag/chat。服务端先 toolGuard(searchDocs) 再检索。
服务端 buildRagPrompt 会再拼当前 question；若 prior 仍含末条 user，模型会看到重复问句。rag_meta 与 delta 分开，避免只靠拼字丢 hits。

用户操作：send / retry / stop / clear

send
async function send(content: string): Promise<void>

做什么：用户点发送或回车时的入口。先落 user 气泡并落盘，再按 ragMode 选择 runRag 或 runStream。

  1. trim；空串或已在 streaming 则直接 return。
  2. 构造 user ChatMessage（createId + createdAt）。
  3. history = [...messages, userMessage]，写回 messages，并 persistCurrentHistory()。
  4. ragMode ? await runRag(history, model) : await runStream(history, model)。
方向名称说明
入参content输入框原文；内部 trim
上下游：输入区组件调用。后续进入 runSseSession 骨架。
先落 user 再开流，保证刷新或中途失败时至少能看到用户原话；streaming 互斥防止双开 SSE。
retry
async function retry(): Promise<void>

做什么：去掉末尾失败/空的 assistant（若有），用最后一条 user 再跑同一链路，不新增 user 气泡。

  1. streaming 中直接 return。
  2. 若末条是 assistant，则 slice 掉；否则保留当前列表。
  3. 校验：非空且末条必须是 user，否则 return。
  4. 按 ragMode 再调 runRag 或 runStream。
上下游：UI「重试」按钮。复用同一条 user，避免历史里叠两个相同问句。
失败气泡往往是空壳或错误文案；保留它再发会污染上下文。剥掉再跑与用户「再试一次」心智一致。
stop
function stop(): void

做什么：中止当前 SSE。对活跃的 AbortController 调用 abort；runSseSession 收尾逻辑会识别 aborted 并可能写入「已停止生成。」。

  1. abortController?.abort()；无进行中请求时为空操作。
上下游：UI 停止按钮、clear() 内部也会先 stop。fetch 的 signal 来自同一 controller。
用标准 AbortSignal 打断 fetch/reader，比自建「忽略后续事件」标志更干净，也不会把迟到的 delta 误写进新一轮气泡。
clear
function clear(): void

做什么：清空当前模式会话：停流、清空消息与过程状态，并把当前模式历史写成空数组。

  1. stop() 打断可能进行中的请求。
  2. messages / error / toolTrace / lastUsage 归零。
  3. localStorage.setItem(historyKey(ragMode), "[]")——只清当前模式，另一模式历史保留。
「清空」应对应当前教学链路；若连 RAG 历史一并删掉，学员切回资料问答会困惑「对话哪去了」。

人工确认：resolveToolConfirm

resolveToolConfirm
async function resolveToolConfirm(payload: { confirmId: string; toolCallId: string; action: "allow" | "deny" }): Promise<void>

做什么：过程面板点「允许 / 拒绝」时调用。只做 UI 状态标记 + POST 确认接口；不会在这里继续跑工具，也不会再发一轮聊天。后续 tool_result / delta 仍走原未结束的 SSE（runStream 里的 streamChat 循环）。

  1. 把匹配的 pending_confirm 行 status 标成 resolving（按钮不可再点）。
  2. await confirmChatTool(payload) → POST /api/chat/confirm，解开服务端 ConfirmSession 的 wait。
  3. 失败则写 error，并把该行 status 恢复为 pending 便于重试。
  4. 成功后：服务端推 confirm_resolved / tool_result / 后续 delta；前端 onTrace 会更新 pending 行，无需再 send。
方向名称说明
入参confirmId服务端确认会话 id
入参toolCallId对应工具调用 id，用于匹配 Trace 行
入参actionallow 或 deny
上下游：ToolTracePanel 按钮 → confirmChatTool。前提：原聊天 SSE 仍挂着（isStreaming true）。资料问答无人工确认，不会走到此函数。
确认闸门在服务端 await wait；前端若再 send 会开第二条 SSE，confirm 会话对不上且会 404。把「点确认」与「继续生成」解耦，是单连接编排的关键设计。

Setter：模型与模式开关

changeModel
function changeModel(nextModel: string): void

做什么：切换当前模型 id，并持久化到 MODEL_KEY。不中断正在进行的流（下次 send 才生效）。

  1. model.value = nextModel。
  2. localStorage.setItem(MODEL_KEY, nextModel)。
模型选择是偏好而非会话身份；与历史消息分开存，避免「换模型却丢聊天记录」。
setSearchKb
function setSearchKb(next: boolean): void

做什么：切换「搜索知识库（必检索）」开关，写入 SEARCH_KB_KEY（"1"/"0"）。单 Agent → 语义 C prefetch；多 Agent → forceKbSearch。

  1. 更新 searchKb ref 并落盘。
  2. 仅影响后续 runStream 请求体；不改 multiAgent，也不改 endpoint。
与多 Agent 解耦：学员可单独观察「单 Agent + 语义 C 强制检索」或「多 Agent + forceKb」行为，而不被强制切到另一路由。
setMultiAgent
function setMultiAgent(next: boolean): void

做什么：切换是否走多 Agent 端点；true 存 "1"，false 存 "0"。缺省未写过 key 时初始化为 true。

  1. 更新 multiAgent ref 并落盘。
  2. 下一次 runStream → streamChat 据此选 /api/chat/multi 或 /api/chat。
用「显式存过 0」判定单 Agent，让第一次打开仓库的学员直接看到多 Agent 路径（教学默认值）。
setRagMode
function setRagMode(next: boolean): void

做什么：在普通对话与资料问答之间切换。先落当前历史，再载入另一条链路的历史，并清空过程态。

  1. 若 next 与当前相同，或正在 streaming，直接 return（流式中禁止切换）。
  2. persistCurrentHistory() 保存当前模式。
  3. 更新 ragMode 与 localStorage RAG_MODE_KEY。
  4. messages = loadHistory(historyKey(next))。
  5. 清空 error / toolTrace / lastUsage（过程面板属于「当前这次请求」，不应带到另一模式）。
上下游：顶栏模式切换。互斥两条会话空间，对应两套 HISTORY 键。
两条链路的 system / 工具 / 资料语义不同，混历史会让学员误以为「同一会话」。流式中禁止切换，避免 abort 与换盘竞态。
